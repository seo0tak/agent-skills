# 작업 이력과 실행 로그

현재 결과는 “지금 어디까지 했는지”, 작업 이력은 “어떤 과정을 거쳤는지”를
보여줍니다. `security-results/`, `data/progress.json`, `data/resume-state.json`의
역할은 유지하고, 별도 누적 기록으로 이전 판단·메모·실패·재시도를 보존합니다.

## 무엇을 남기나요?

| 기록 | 내용 |
|---|---|
| 작업 시작·종료 | 작업과 시도 식별자, 항목, 기록 시각, 실제 확인한 결과 |
| 실패·차단·중단 | 발생 단계, 확인된 오류 요약, 다음 조치와 근거 |
| 중요한 변경 | 상태·결론·처리 범위·정책 등의 변경 전후와 이유 |
| 변경 발견 | 이전 관측값과 다른 결과·진행·정책 파일, 확인한 시각 |
| 브라우저 검토 | 화면에서 저장한 상태·메모·결과 초안 변경과 출처 |

기록된 명령이 정상 종료했다고 취약점 검증까지 통과한 것은 아닙니다.
검증 완료는 기존 snapshot → 실제 검증 → 결과 기록 → seal-verification
절차와 현재 소스 대조가 필요합니다. 로그의 수행 주체도 사용자 권한의 증명은 아닙니다.

## 저장 위치와 보존

- `data/activity/`: 월별 디렉터리의 개별 이벤트 JSON이 누적 기록의 정본입니다.
- `data/activity.js`: 체크리스트가 읽는 생성물입니다. 원본 이벤트를 편집하는 파일이 아닙니다.
- 브라우저 백업의 `activityEvents`: 브라우저에서 저장한 이력입니다.
  프로젝트 파일로 가져오기 전에는 그 브라우저와 내려받은 백업에만 있습니다.

이벤트는 기존 내용을 고치거나 자동 삭제하지 않습니다. 잘못된 판단은 정정 사유를
새 기록으로 남깁니다. 같은 작업의 재시도는 같은 논리 작업에 새 시도를 연결하고,
동일한 이벤트를 다시 가져오는 것은 중복 저장하지 않습니다. 동일 ID에 다른 내용이
있으면 충돌로 처리합니다. 필터 변경·처리 범위 축소·차수 변경은 과거 이력 삭제가 아닙니다.

이력은 요약과 근거 참조를 보관합니다. 긴 문자열·큰 전후 상태는 크기 제한에 따라
축약되며 이벤트 한 건은 최대 32 KiB입니다. 축약 표시가 있으면 참조한 원본·백업도
함께 보존하세요. 전체 소스·긴 검증 출력의 영구 보관을 대신하지 않습니다.

월별 분리는 조회 가능한 보관 단위입니다. 별도 보관 폴더로 임의 이동하면 도구가
찾지 못할 수 있으므로 원래 구조를 유지해 백업합니다. 로컬 파일만으로 디스크 손실,
무단 변경 방지, 외부 백업이나 법적 보존을 보장하지는 않습니다.

## 종료 기록이 없을 때

작업 시작을 먼저 저장하고 실제 종료를 나중에 저장합니다. 강제 종료·전원 상실·
네트워크 단절 순간에는 마지막 기록을 남길 수 없으므로 시작만 남을 수 있습니다.
이 경우 표시하는 것은 **종료 확인 없음**이지 “실패 확정”이나 “현재 실행 중”이 아닙니다.

재개할 때는 기록된 작업·항목·마지막 근거와 현재 파일, 실제 실행 중인 작업자가
있는지를 대조합니다. 확인하지 않은 중단 원인과 정확한 종료 시각을 만들어 넣지 않습니다.
재시도 전에 이미 반영된 수정이 있는지 확인해 같은 패치를 중복 적용하지 않습니다.
읽기 전용 조회가 미종료 작업을 자동으로 성공·실패 처리하지 않습니다.

기록 저장에 실패하면 새 변경을 시작하지 않습니다. 변경 후 종료 기록 저장에
실패했다면 이미 바뀐 파일이 있을 수 있으므로 완료 보고를 보류하고 대조합니다.
소스·결과·진행상태·로그 전체를 한 번에 되돌리는 트랜잭션이나 소스 롤백 기능은 아닙니다.

## AI가 수정·검증할 때의 기록 순서

툴킷 디렉터리에서 실행합니다. `<ID>`는 실제 항목 ID로 바꾸고,
반환된 `operationId`와 `attemptId`를 해당 작업에 연결합니다.

```text
python3 tools/sast_activity.py start --action remediation --id <ID> --actor agent --summary "승인된 항목의 소스 조치 시작"
```

시작 기록이 성공한 뒤 기존 03 절차의 체크포인트 → 수정 → 체크포인트를 수행합니다.
현재 파일·결과를 확인한 후 해당 수정 작업의 실제 결과를 기록합니다.

```text
python3 tools/sast_activity.py finish --attempt-id <반환된 attemptId> --outcome succeeded --summary "승인된 수정 적용 및 결과 기록; 검증은 별도"
```

외부 검증도 별도 시도로 시작합니다. snapshot은 기존 검증 연결 절차에 따라 저장하고,
검증 명령을 실제 실행한 뒤 결과 JSON과 로그에 각각 실제 수준을 남깁니다.

```text
python3 tools/sast_activity.py start --action verification --id <ID> --actor agent --summary "변경 영향 범위 검증 시작"
python3 tools/sast_activity.py finish --attempt-id <검증 attemptId> --outcome failed --summary "관련 테스트 실패; 오류 근거와 재시도 조건은 항목 결과에 기록"
```

위 실패 종료는 예시이며 실제 통과했으면 `succeeded`, 입력·권한 등의 조건으로
실행을 차단했으면 `blocked`, 직접 확인한 사용자 중단이면 `stopped`를 사용합니다.
완료하지 못한 검증을 succeeded로 기록하지 않습니다. 오류 요약에 비밀값을 넣지 않습니다.
수정 작업이 완료됐지만 검증이 실패한 경우 두 시도의 서로 다른 결과를 유지합니다.

재시도는 이전 `operationId`를 `start --operation-id <값>`에 전달하고 새
attemptId를 받습니다. 같은 작업공간·차수·작업 종류·대상 항목의 재시도에만
기존 operationId를 사용합니다. 수정과 검증, 무관한 항목은 별도 작업입니다.
담당자가 바뀌었다고 동일 작업의 이력을 새로 시작할 필요는 없습니다.
동일 시도를 다시 기록하려면 원래 attemptId와 같은 내용을
사용합니다. 먼저 저장된 결과와 충돌하면 원본을 유지하고 확인합니다.

조회는 원본을 바꾸지 않습니다.

```text
python3 tools/sast_activity.py status
python3 tools/sast_activity.py query --id <ID>
```

`unfinishedCount`와 `unfinishedAttempts`는 종료 확인이 없는 시도입니다.
실패·차단·중단 건수는 과거 이력 집계이며 현재 취약점의 미해결 건수가 아닙니다.
다른 작업자가 아직 실행 중인지 확인하지 않고 미종료 시도를 강제로 닫지 않습니다.
나중에 실제 결과를 확인했다면 현재 시각에 확인한 내용을 적어 종료하고,
과거의 정확한 종료 시각·원인을 알고 있는 것처럼 기록하지 않습니다.

## 자동 기록의 경계

중요한 확인 사실은 다음처럼 별도 기록할 수 있습니다. 설명에는 실제로 확인한
내용과 남은 한계를 적고, 원인을 모르면 모른다고 적습니다.

```text
python3 tools/sast_activity.py note --action review --id <ID> --actor agent --summary "현재 소스 대조 결과와 남은 확인 사항" --important
```

초기화된 프로젝트 또는 명시적으로 작업 기록을 시작한 툴킷에서 변경 명령의
시작·종료를 자동 기록합니다. 배포용 미초기화 툴킷을 검사·동기화하는 것만으로
실제 작업 로그를 만들지는 않습니다. 그 이전의 오류는 명령 출력으로 확인합니다.

AI의 소스 수정과 외부 테스트는 툴킷 프로세스 밖에서 일어납니다. 해당 작업은
시작·종료 명령으로 직접 연결해야 하며 툴킷이 모든 에디터·셸·세션을 감시한다고
표현하지 않습니다. 직접 바뀐 정본은 다음 대조에서 **변경 발견**으로 기록합니다.
발견 시각은 실제 수정 시각이 아니며, 발견만으로 수행 주체나 변경 이유를 알 수 없습니다.
처음 관측한 자료는 도입 시점의 기준 상태입니다. 도입 전 이력을 추정해 채우지 않습니다.

정본을 직접 변경한 뒤에는 `sync` 또는 다음 명령으로 차이를 기록합니다.
`status`의 `baselineRequired`는 아직 기준 관측이 없다는 뜻이고,
`driftCount`·`canonicalChanges`는 마지막 관측 이후의 차이입니다.

```text
python3 tools/sast_activity.py reconcile
```

`canonical.reconcile`은 도구 내부 관측용 이름입니다. 일반 메모나 브라우저
이력에 이 이름을 넣어 파일 대조를 대신하지 않습니다.
이 명령은 현재 파일을 대조해 이력을 추가합니다. 결과의 적정성이나 변경 권한을
승인하지 않으며, 소스 파일의 모든 편집 과정을 복원하지 않습니다. 두 번의 대조
사이에 여러 번 덮어쓴 중간 상태는 알 수 없으므로 중요한 판단은 즉시 기록합니다.

## 체크리스트에서 보기

기본 화면은 **작업 이력**입니다. 사용자가 확인할 작업과 상태 변화를 먼저 보여주고,
내부 처리 과정은 **시스템 운영 기록**, 기술 정보는 **진단 상세**로 나눕니다.

| 화면 | 확인할 내용 |
|---|---|
| 작업 이력 | 검토·수정·검증 시도, 상태·판정·메모·처리 범위 등의 변경과 기록된 이유 |
| 시스템 운영 기록 | 동기화·체크포인트·스냅샷·기준 관측 같은 내부 처리와 원본 기록 |
| 진단 상세 | 해당 작업의 원래 이벤트, 식별자·경로·상세 전후 값·오류 내용 |

실제 조치·상태 변경을 보려면 작업 이력을 사용합니다. 내부 저장 과정을 확인할 때만
시스템 운영 기록을 펼치고, 원본이 필요하면 해당 기록의 진단 상세를 펼칩니다.
항목 상세도 작업 이력을 우선하며 현재 작업공간·차수의 해당 ID로 한정합니다.
이전 차수는 전체 작업 이력에서 차수 표시와 함께 확인합니다.

같은 작업임을 식별할 수 있는 시작·종료·재시도는 묶어 보여줍니다. 과거 실패와
재시도 결과는 각각 남으며, 수정과 검증은 다른 작업입니다. 작업 성공 기록만으로
취약점 검증 완료를 만들지 않습니다. 브라우저에서 상태를 바꾼 기록도 실제 소스 수정과
구분합니다. 변경 발견은 관측 시각의 대조 결과이며 실제 수정 시각·주체가 아닙니다.

정상적인 내부 처리는 기본 목록에서 줄이지만, 저장 실패·차단·종료 미확인처럼
작업에 영향을 줄 수 있는 기록은 사용자에게도 확인 사항을 알립니다. 과거 오류
건수를 현재 미해결 취약점 건수로 해석하지 않습니다. 분류할 근거가 부족한 옛
기록은 **분류 미확인**으로 조회할 수 있으며 임의로 정상·완료 처리하지 않습니다.

이 구분은 저장된 내용을 바꾸는 작업이 아닙니다. 기록 출처·실행 결과·중요 표시와
화면의 용도는 별개이고, 필터 변경도 원본 이력·검출 목록·승인된 처리 범위를 바꾸지
않습니다. 원본 이벤트와 백업은 그대로 보존합니다. 진단 상세는 이미 저장된 정보를
보여주며, 별도 디버그 수집이나 전체 실행 환경·원시 소스 수집을 켜는 기능이 아닙니다.

목록은 페이지당 50개로 나누고 높이가 제한된 영역에서 스크롤합니다. 파일 기록과
브라우저 임시 기록을 구분하고 생성 시각·불러온 시각을 확인합니다. 화면은 실시간
감시기가 아닙니다. 누락·축약된 정보는 진단 상세와 참조 원본을 대조하세요.

브라우저 상태·초안·이력은 함께 저장하고 상태+결과 백업으로 보관합니다.
내려받기나 파일 로그에 이력을 가져오기만으로 결과 정본을 변경하거나 검증 완료로
올리지 않습니다. 정본 반영은 04 절차로 출처·근거를 대조합니다.
저장 실패가 표시되면 창을 닫기 전에 백업하고 실제 파일이 저장됐는지 확인하세요.
동일 프로젝트를 여러 탭에서 동시에 편집하지 마세요. 저장 직전 확인 가능한
이력은 합치지만, 탭 간 완전한 동시 저장이나 상태 충돌 해결을 보장하지는 않습니다.

백업 원본과 출처를 확인한 뒤 브라우저 이력만 파일에 보관하려면 다음을 실행합니다.

```text
python3 tools/sast_activity.py import-browser --file <상태와 결과 백업 JSON>
```

이 명령은 이력 보관입니다. progress와 결과를 대신 반영하지 않습니다. 같은
작업공간의 과거 차수 이력은 원래 reportId를 유지하며, 다른 작업공간이나 동일
이벤트 ID의 다른 내용은 거부합니다. 상태·결과 초안은 04 절차로 따로 대조합니다.

## 민감정보와 손상 기록

기록에는 필요한 요약과 근거 참조만 넣습니다. 비밀번호·토큰·환경변수 전체,
원시 응답·전체 소스는 넣지 않습니다. 알려진 비밀 필드의 마스킹은 모든 민감정보를
찾아내는 보장이 아니므로 작성자도 확인해야 합니다.

손상 파일·ID 충돌·다른 작업공간의 이력은 정상 기록처럼 합치지 않습니다.
문제가 있는 원본을 보존하고 오류를 확인한 뒤 복구합니다. 읽을 수 없는 이력을
