# 동작 원리 (How It Works)

이 문서는 스킬과 툴킷이 "왜 이렇게 움직이는지"를 설명합니다. 순서대로
따라 하는 절차는 `USAGE.md`, 단계별 세부 규칙은
`SECURITY_SAST_WORKFLOW.md`를 보세요.

## 한 줄 요약

스캐너가 아니라 **받은 SAST 결과를 조치·오탐검토·검증·증적까지 관리하는
파일 기반 워크플로우**입니다. AI가 실행자, 사람은 정책 결정자, 파일이
상태 저장소, 검증기가 심판 역할을 합니다.

## 구성 요소와 역할

```text
[스킬]  ~/.claude/skills 또는 플러그인
  └─ 트리거 감지 → 툴킷을 프로젝트에 복사 → 워크플로우 지휘

[툴킷]  <프로젝트>/sast-remediation-toolkit/
  ├─ prompts/       단계별 요청문 (00~07) — AI에게 주는 작업 지시서
  ├─ tools/         sast_toolkit.py — 게이트·동기화·검증 (표준 라이브러리만)
  ├─ schemas/       모든 산출물의 데이터 계약
  ├─ input/         이번 차수의 보고서 (사람이 넣음)
  ├─ project/       분석·정책·결정 로그 (읽는 문서)
  ├─ data/          대시보드용 데이터 (findings, progress 등)
  ├─ security-guides/   항목별 사전 검토 (수정 전 안전 범위)
  ├─ security-results/  항목별 조치 결과 ← 상태의 기준(canonical)
  └─ evidence/      제출용 증적 워크북
```

## 핵심 원리 6가지

### 1. 게이트가 모든 것에 선행한다

잘못된 입력(다른 프로젝트, 다른 차수, 손상 파일)에 분석을 낭비하지
않도록, 시작 전에 두 겹으로 확인합니다.

- **기계 점검**(preflight): 파일 개수·시그니처·소스 존재를 도구가 검사
- **의미 대조**(AI): 프로젝트 키, 분석 ID, 검출 건수, 소스 경로 표본
  일치율을 근거와 함께 판정

판정은 `data/input-validation.json`에 기록되고, `gate` 명령이 기록과
**현재 입력 파일을 재대조**합니다. 입력 파일이 하나라도 바뀌면 이전
승인은 자동 무효 — "승인해 놓고 파일 바꿔치기"가 구조적으로
불가능합니다.

### 2. 상태는 2차원이고, 기준은 results다

- **진행상태**(어디까지 했나): todo → in-progress → analyzed →
  change-complete → verified / deferred
- **결론**(무엇으로 판정했나): fix / false-positive / operations /
  exception / needs-review

이 둘을 분리해서 "검증 안 된 수정"과 "검증 끝난 오탐 판정"을 정확히
구분합니다. 진실의 원천은 항목별 `security-results/<ID>.json`이고,
`data/progress.json`은 대시보드용 집계입니다. 두 저장소가 어긋나면
`validate`가 에러를 냅니다.

### 3. JSON이 기록, JS는 미러

기계가 읽는 기준 기록은 JSON입니다. 그런데 브라우저는 `file://`에서
로컬 JSON 요청을 막기 때문에, `sync` 명령이 같은 내용을 `.js` 파일로
미러링해 대시보드가 `<script>`로 읽습니다. **대시보드가 안 바뀌면
십중팔구 sync 미실행**입니다. 미러가 원본과 어긋나는 것도 validate가
잡습니다.

### 4. 대시보드는 보는 곳이자 사람의 입력 통로

열리는 순간 항목별 결과가 자동 반영되고(2번 원리 — results가 기준),
사람이 화면에서 바꾼 상태는 브라우저(localStorage)에 임시 저장됩니다.
파일과 브라우저가 어긋나면 항목별 `updatedAt`이 최신인 쪽이 이기고,
충돌 건수가 상단 배너에 표시됩니다. 브라우저에만 있는 변경은 [상태
백업]으로 내려받아 AI에게 전달하면(04 프롬프트) results에 근거와 함께
흡수됩니다.

### 5. 판단 근거는 소스가 우선, 정책은 한 번만 묻는다

보고서 라인이 어긋나면 현재 소스에서 검출 구문을 다시 찾습니다(소스
매핑: 일치/이동/변경/미발견). 코드로 판단할 수 없는 것만 한 번에
하나씩 질문하고, 답은 `PROJECT_SECURITY_POLICY.md`와
`DECISION_LOG.md`에 기록되어 이후 같은 질문이 반복되지 않습니다 —
세션이 바뀌어도(07 재개) 확정 정책은 재사용됩니다.

### 6. 차수가 바뀌어도 판정은 이월된다

검출 ID는 차수마다 바뀌는 임의 번호라 쓸 수 없습니다. 대신 소스에
매핑된 모든 검출에 `fingerprint`(파일·함수·검출 구문 지문)를 기록하고,
다음 차수에서 지문 매칭으로 오탐·예외 결론을 승계합니다(06). 코드가
바뀐 항목은 자동 승계하지 않고 재검토로 강등 — "작년에 오탐이었으니
올해도 오탐" 같은 무근거 승계를 막습니다. 사람 간 소통과 증적에서는
지문에서 파생된 `stableKey`(SK-xxxxxxxx)가 차수를 넘는 고정 명칭
역할을 합니다.

### 7. 작업 난이도에 따라 모델 티어를 나눈다 (선택)

플러그인에는 모델이 고정된 서브에이전트 2종이 포함됩니다.

| 에이전트 | 모델 | 담당 | 금지 |
|---|---|---|---|
| sast-bulk-worker | haiku | 멤버 delta 가이드, progress 집계, 증적 행, sync/validate | 소스 수정, 결론 판정, 정책 해석 |
| sast-remediator | sonnet | 승인된 가이드 범위 내 소스 수정 + 검증 실행 | 가이드 없는 항목, verified 승격 |
| (메인 세션) | 사용자 선택 | 결론 판정, 정책 근거, 회귀 분석, verified 승격 | — |

설계 이유: 특성 파악을 실행 중에 하는 대신 **역할을 미리 고정**했습니다.
저비용 티어에는 validate가 결과를 기계로 검사할 수 있는 작업만 배정되어
품질 리스크가 없고, 서브에이전트의 분리된 컨텍스트 덕에 메인 세션이
수천 건 데이터로 비대해지지 않아 같은 모델을 써도 토큰이 절약됩니다.
서브에이전트나 해당 모델이 없는 환경에서는 자동으로 메인 세션이 전부
수행하므로 기능 차이는 없습니다.

### 8. 중단에 강하다

- **전원이 꺼져도** 처음부터 하지 않습니다. 항목이 완료될 때마다
  `security-results/<ID>.json`이 즉시 기록되므로, 새 세션에서 07 재개가
  파일 상태 그대로 이어갑니다. 잃는 것은 진행 중이던 항목 1개 분량.
  대화 자체도 Claude Code가 로컬에 트랜스크립트를 남겨 복원 가능합니다.
- **네트워크 오류**는 그 턴만 끊습니다. 툴킷은 작업 중 네트워크를 쓰지
  않고(로컬 파일+로컬 명령, 대시보드도 file://), 이미 쓴 파일은 그대로
  남습니다.
- **쓰다 만 파일**(반쪽 JSON)은 validate/sync가 파일명을 지목하고,
  도구 자신의 쓰기는 임시 파일+교체 방식이라 반쪽이 생기지 않습니다.
  복구 규칙: results/guides는 해당 항목만 재작성, progress는 results에서
  재생성(기준이 results라 손실 없음), 미러는 sync가 재생성.

## 한 차수의 생애

```text
사람: input/에 보고서 투입
AI  : [00] preflight → 의미 대조 → gate READY
AI  : [01] 프로젝트 분석 + 검출 정규화 + 소스 매핑     ← 사람: 승인
AI  : [06] 이전 차수 있으면 fingerprint 이월
루프: [02] 정책 질문(수시, 사람이 답) ↔ [03] 웨이브(그룹 가이드
      → 소스 조치 → 검증 method 기록) — 세션 끊기면 [07]로 재개
AI  : [04] 대시보드 인적 변경 흡수 + 근거 보강
AI  : [05] 증적 4종 생성(templates/ 컬럼 고정)          ← 사람: 확인
도구: validate --strict OK → 제출
```

## 지식 산출물은 OKF 호환

`project/` 아래 마크다운 산출물(분석, 정책, 결정 로그, 작업 그룹)은
구글 클라우드의 Open Knowledge Format 호환 frontmatter(type 필수,
title·description·timestamp·tags 권장)로 생성되고, `project/index.md`가
디렉터리 목록, `DECISION_LOG.md`가 시간순 로그 역할을 합니다. 상태
데이터(JSON)는 스키마 강제가 필요해 OKF 대상이 아닙니다. frontmatter가
없어도 워크플로우 동작에는 영향이 없으며(소프트 적용), 이렇게 해두면
프로젝트별 SAST 정책·결정 지식을 조직 지식 카탈로그나 다른 에이전트가
그대로 수집할 수 있습니다.

버전·호환 정책(하위호환 원칙, 진행 중 차수 업그레이드 규칙, breaking
변경 절차)은 `docs/VERSIONING.md`에 있습니다.

## 무엇이 이걸 지키게 하나

규칙은 문서가 아니라 도구가 강제합니다. `validate`가 잡는 것:
게이트 미통과(strict), 중복 ID, 잘못된 enum, progress↔results 불일치,
JSON↔JS 미러 드리프트, 스키마↔검증기 enum 불일치, 스키마↔검증기
schemaVersion 불일치, 산출물 schemaVersion 불일치(단일 파일은 에러,
레코드류는 경고), fingerprint 누락, 검증 없는 verified,
method 없는 verified(경고), 필수 파일 누락.
AI가 규칙을 잊어도 validate가 빨간불을 켭니다.
