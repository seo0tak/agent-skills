# 동작 원리

받은 SAST 검출 결과를 조치·오탐 검토·검증·증적까지 관리하는
파일 기반 워크플로우입니다. AI가 승인 범위에서 실행하고, 사람은
업무 정책과 중요한 변경을 결정합니다. 도구는 데이터 정합성을 검사합니다.

따라 하는 순서는 `USAGE.md`, 세부 규칙은
`SECURITY_SAST_WORKFLOW.md`, 업그레이드는 `VERSIONING.md`를 참고하세요.

## 1. 입력 승인과 소스 검증은 별개입니다

입력은 대상 프로젝트의 현재 작업 사본(이하 "현재 소스")과 한 차수의
보고서 세트입니다.
상세 보고서 PDF 1개 이상 + 스프레드시트 1개(Sparrow 보고서 기준 안내 포함),
또는 SARIF 1개를 받습니다.
SARIF의 PDF는 선택 사항입니다.

`preflight`는 파일 개수·형식·소스 존재를 확인합니다.
AI는 프로젝트·차수·검출 건수·소스 범위를 실제 내용으로 대조합니다.
`gate`는 승인 기록의 입력 경로·크기·SHA-256을 현재 자료와 비교합니다.
입력이 바뀌면 이전 승인은 그대로 사용할 수 없습니다.

이 게이트는 입력 세트를 연결합니다. 이후 현재 소스가 바뀌었는지는
항목별 검증 스냅샷으로 따로 검사합니다. 두 검사 모두 의미 판정이나
실제 테스트의 정당성을 대신 증명하지는 않습니다.

## 2. 상태는 두 차원이며 기록 종류를 구분합니다

진행상태는 작업 단계, 결론은 판단 종류입니다.
예를 들어 `change-complete/fix`는 수정했지만 검증을 마치지 않은 상태입니다.
`verified/false-positive`는 오탐 판단까지 검증한 상태입니다.

| 기록 | 기준이 되는 정보 |
|---|---|
| `security-results/<ID>.json` | 항목별 결론·변경·검증 결과 정본 |
| `data/progress.json` | 결과와 일치해야 하는 집계 및 아직 결과가 없는 임시 진행상태·비고 |
| `data/resume-state.json` | 중단 지점·다음 작업·파일 스냅샷 |
| `data/decisions.json` | 정책 결정·주체·적용 범위·재검토 조건 |
| 브라우저 저장·백업 | 사람이 검토한 상태와 상세 결과 초안 |
| JS 미러·index·결정 로그 | 위 정본에서 다시 만드는 읽기용 생성물 |

완료 상태나 확정 결론에는 결과 레코드가 필요합니다.
반면 `todo/in-progress` 등 일부 임시 상태는 결과 없이 유효합니다.
따라서 progress 전체를 results만으로 복구할 수는 없습니다.

## 3. JSON이 정본이고 JS는 화면용 사본입니다

로컬 파일 화면에서 JSON 접근이 제한되는 환경을 위해 `sync`가
JSON을 JS 미러로 생성합니다. 화면이 갱신되지 않으면 sync 결과와
브라우저의 파일 접근 오류를 확인하세요. validate는 미러 드리프트도 검사합니다.

`USAGE.html`은 `USAGE.md`와 `assets/usage.css`에서 생성합니다.
내장된 제한형 Markdown 렌더러는 제목·문단·중첩 목록·표·코드·강조·안전한
링크 등 일부 Markdown 요소를 변환합니다. 원문 HTML과 스크립트는 실행하지
않습니다.

## 4. 브라우저 초안은 파일 결과가 아닙니다

답변에서 추출한 상세 결과는 진행상태와 함께 같은 localStorage 항목에 저장합니다.
기존 `schemaVersion: "1.0"` 백업에 선택 필드 `draftResults`를 추가했습니다.
각 값은 `{source: "browser-answer", savedAt, result}`이며 result에는
diff·파일·판단 이유·검증 등 추출한 전체 상세가 들어갑니다.

가져오기는 작업공간·ID·필드 형식을 먼저 검사합니다.
다른 작업공간 또는 잘못된 초안을 일부만 합치지 않습니다.
옛 상태 백업도 읽을 수 있지만, 원래 없던 상세 결과를 복원할 수는 없습니다.

파일과 브라우저 상태는 항목 시각을 기준으로 비교하며, 차이는 화면에 표시합니다.
상세 초안의 정본 일치 여부와 검증 결과는 별도 표시합니다.
다운로드는 브라우저 밖 백업을 만든 것일 뿐 정본 반영의 증거가 아닙니다.
04 절차에서 출처·현재 소스·근거를 확인하고 반영해야 합니다.

저장소 삭제, 시크릿 모드 종료, 용량 제한이나 브라우저 정책은 별도 위험입니다.
원본 백업을 보관하고 저장 실패 표시를 확인해야 합니다.
읽지 못한 현재 저장본은 자동 저장으로 덮어쓰지 않고 원문 백업 버튼을 제공합니다.
불러오기 전에 원문과 현재 화면의 새 초안을 각각 내려받고, 실제 파일이 생성되어
열리는지 사용자가 확인해야 합니다. 화면 메시지만으로 다운로드 성공을 보장하지
않습니다. 이 백업은 정상 자료로 변환하거나 권한을 부여하지 않습니다. 두 원본을
보존한 뒤 유효한 백업을 명시적으로 불러옵니다. 일반적인 불러오기는 항목별
`updatedAt`을 비교해 병합하고 더 최신인 현재 값을 유지합니다. 읽지 못한 저장본을
보호 중이었다면 성공한 불러오기가 그 보호 대상 브라우저 저장 항목을 검사·병합한
내용으로 교체합니다.

## 5. 중단 후에는 저장된 범위만 복구합니다

`sast_state.py`는 자동 실행기가 아니라 수동 재개를 돕는 도구입니다.

- `checkpoint`: 수정 전·후의 진행상태, 비고, 다음 작업과 대상 파일을 저장
- `snapshot`: 검증 직전 대상 파일 내용을 해시로 기록
- `seal-verification`: 실제 통과 기록과 현재 소스를 스냅샷에 연결
- `status`: 읽기 전용으로 미완료 작업·검증 연결 상태를 확인
- `recover-progress`: 복구 내용을 먼저 보여주고 `--apply`일 때만 반영

수정 전 체크포인트와 현재 diff를 대조하면 중간 수정을 찾는 데 도움이 됩니다.
체크포인트는 소스 백업이나 패치 롤백 기능이 아닙니다.
결과·체크포인트·백업에 없는 진행 메모는 복구할 수 없습니다.
원본 손상 파일과 복구 자료는 보존하며 모호한 충돌을 임의로 덮어쓰지 않습니다.

도구 쓰기는 같은 디렉터리의 고유 임시 파일과 원자적 교체를 사용합니다.
협조하는 작성자는 공통 잠금으로 조정하고 파일을 동기화합니다.
에디터·외부 프로세스는 이 잠금을 따르지 않을 수 있으므로 공용 정본에는
한 작성자를 지정합니다. 여러 파일 전체의 트랜잭션, 전원 장애·네트워크
파일시스템의 내구성, 클라우드 동기화 충돌까지 보장하지는 않습니다.
정본이 온전하면 중간에 끊긴 미러 생성은 sync로 다시 실행할 수 있습니다.

모델 호출이나 원격 테스트가 네트워크를 사용하면 연결 중단의 영향을 받습니다.
툴킷이 자동 재접속·재시작·대기·감시를 수행하지는 않습니다.
실행 환경이나 사용자가 재개한 뒤 07 절차를 사용합니다.

## 6. 검증 완료는 현재 파일과 연결합니다

결과의 선택 필드 `verification.sourceSnapshot`에 작업공간·프로젝트 루트·
검증 전 시각·대상 파일 해시와 근거 연결 정보가 기록됩니다.

- `fresh`: 지정한 파일과 저장된 검증 근거가 여전히 일치
- `stale`: 파일·근거·연결 조건이 달라져 재검증 필요
- `unbound`: 옛 verified 결과에 연결 정보가 없어 현재 검증으로 신뢰할 수 없음
- `not-verified`: 검증 완료 결과가 아님

도구가 테스트를 실행해 주는 것은 아닙니다.
AI가 검증 직전 snapshot을 만들고 실제 검증을 수행한 뒤, 시각·방법·결과를
기록해야 연결할 수 있습니다. 과거 passed 문구만으로 새 검증을 만들지 않습니다.
선택하지 않은 파일·외부 서비스·DB·운영 정책은 별도 근거가 필요합니다.

옛 결과는 형식 호환을 위해 읽을 수 있습니다. validate 경고가 남을 수 있고,
status에서는 재검증 후보로 나타납니다. 완료·제출 판단에서는 이 차이를 숨기지 않습니다.

## 7. 차수 간 결론과 정책은 유효할 때만 재사용합니다

fingerprint는 동일 항목의 후보를 찾습니다. 약한 매칭이나 다중 후보는
현재 소스에서 대조해야 하며 ID만으로 이월하지 않습니다.
오탐·예외는 이전 검증과 현재 코드·정책·외부 규격의 유효성을 확인합니다.
새 차수의 verified는 현재 소스에서 재검증합니다.
“이번 차수 미검출”은 검사 범위 확인 없이 “해소”로 바꾸지 않습니다.

정책 정본은 decisions.json, DECISION_LOG.md는 읽기용 생성물입니다.
이미 확정된 동일 범위 정책은 세션이 바뀌어도 재사용하되 새 증거나 기한을 확인합니다.
미확인 기본안을 위한 관찰 수단을 추가할 때도 실제 사용자 선택과 변경 범위가 필요합니다.
`observation`과 `reviewTrigger`의 비어 있지 않음을 검사할 수는 있지만,
관찰이 실제로 수행됐는지·조건이 충족됐는지는 도구가 자동 감시하지 않습니다.
정책 재사용과 소스 변경·배포 권한은 서로 다른 문제입니다.

## 8. 위임과 큰 데이터 처리

등록된 Claude Code 에이전트가 있으면 기계 작업은 sast-bulk-worker,
승인된 수정은 sast-remediator에 나눌 수 있습니다.
결론·정책·verified 판단은 메인이 확인합니다.
해당 에이전트가 없는 환경에서는 메인이 같은 절차를 직접 수행합니다.
품질·비용·속도는 환경에서 확인해야 합니다.

query는 필요한 그룹·필드만 반환해 대화에 전체 파일을 올리지 않도록 합니다.
내부에서는 findings와 progress를 읽습니다. 재개 시 todo만 고르지 말고
status의 후보와 그룹의 모든 상태를 함께 확인하세요.

## 9. 문서 메타데이터와 검사의 한계

프로젝트 Markdown은 type·title·description·timestamp·tags를 사용하는
메타데이터 형식을 따릅니다. 이는 저장소의 문서 정리 규약이며 외부 표준이나
모든 지식 수집 도구와의 호환성을 인증하는 것은 아닙니다.

validate는 스키마·ID·enum·상태·미러·입력·연결된 검증 근거의 정합성을 확인합니다.
실제 취약점 판단, 테스트 충분성, 정책의 정당성, 운영 결과와 사용자 승인은
별도 검토 대상입니다. strict OK만으로 안전한 제출을 보장하지 않습니다.
