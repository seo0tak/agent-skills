사용 가이드

이 페이지는 USAGE.md에서 생성한 읽기용 가이드입니다.

받은 SAST 검출 결과를 현재 소스와 대조하고, 조치·검증·증적까지 관리하는 가이드입니다. 처음에는 1번부터, 중단한 작업은 6번부터 확인하세요. 사용자 요청이 없을 때 스스로 실행하거나 배포하는 도구는 아닙니다.

전체 흐름

노란 단계는 사용자가 정하는 지점이고, 점선은 필요할 때 들어가는 단계입니다.

프롬프트 번호는 파일 이름입니다. 작업 순서는 위 흐름을 따르며, 세션이 끊기면 07 재개 절차로 현재 기록부터 확인합니다.

1. 준비와 첫 요청

프로젝트 루트에 툴킷 전체를 sast-remediation-toolkit/ 이름으로 복사하고, input/에 이번 차수 자료를 넣습니다.

  • PDF·스프레드시트 보고서: 상세 PDF 1개 이상 + 검출 목록 스프레드시트 1개 (Sparrow 보고서 기준 안내 포함)

  • SARIF: 표준 .sarif 파일 1개. PDF는 선택 자료입니다.

여러 차수·도구의 자료는 input/<세트명>/으로 분리합니다. 한 차수에는 한 세트만 사용합니다. 여러 세트가 있으면 사용할 세트를 지정하세요.

이 스킬을 설치했고 프로젝트 파일을 읽을 수 있는 AI 도구에서는 “SAST 결과 조치해줘”라고 요청해도 됩니다. Claude Code·Codex 등 환경별 설치 방법은 저장소 README를 따릅니다. 설치본 갱신은 기존 프로젝트 복사본을 바꾸지 않습니다. 업그레이드는 새 설치본의 docs/VERSIONING.md에 따라 별도로 진행합니다.

프로젝트 파일을 읽을 수 있는 AI 도구에는 다음처럼 요청합니다.

sast-remediation-toolkit/prompts/00-preflight.md를 읽고 수행해줘.

파일을 읽거나 수정할 수 없는 일반 채팅에서는 해당 프롬프트의 요청문과 필요한 자료를 전달해야 합니다. AI가 로컬 파일을 수정했다고 가정하지 마세요.

2. 입력 확인과 초기 분석 — 00, 01

AI는 먼저 입력 개수·실제 파일 형식·소스 존재를 검사하고, 전체 입력의 경로·크기·SHA-256을 기록합니다. 그다음 프로젝트 식별정보, 검사 차수, 검출 건수와 소스 범위를 실제 내용으로 대조합니다.

  • GATE: READY: 초기 분석을 진행할 수 있습니다. 소스 변경 승인은 별도입니다.

  • BLOCKED: 차단 사유에 맞게 입력을 보완합니다. 임의로 승인 값을 바꾸지 않습니다.

  • 승인 후 입력을 바꾸거나 옛 승인에 해시가 없으면 00부터 다시 대조합니다.

초기 분석 후에는 다음을 확인하세요.

산출물확인할 내용
project/PROJECT_ANALYSIS.md모듈·빌드·테스트 방법·변경 제한
data/findings.json선택 보고서의 검출 목록과 건수
SECURITY_CHECKLIST.html매핑 상태, 위험도, 작업 그룹과 미확인 항목

“미확인”은 0건이나 문제가 없다는 뜻이 아닙니다. 소스에 매핑한 항목의 fingerprint는 차수 간 대조용 지문이며, 그 자체가 오탐·수정 완료의 증거는 아닙니다.

이번 차수의 처리 범위를 설정합니다

전체 항목을 등록하고 건수를 대조한 뒤 상세 분석·조치할 최소 위험도를 data/project-profile.json에 기록합니다. 범위가 없으면 전체로 자동 실행하지 않습니다. 예를 들어 “높음 이상”은 다음과 같이 설정합니다.

python3 tools/sast_toolkit.py scope --min-risk high --set-by user \
  --reason "이번 차수는 높음 이상 처리"
python3 tools/sast_toolkit.py scope

critical/very-high/high는 대상, 더 낮은 5단계와 info는 범위 밖, unknown·등급 누락은 별도 미확인입니다. 전체 입력·기존 상태는 모두 보존합니다. 정본, 다른 임계값, 재개와 집계 계약은 docs/PROCESSING_SCOPE.md를 참고하세요.

오탐 판단과 조치 필요성은 따로 확인합니다

AI는 먼저 체커가 어떤 조건을 검출하는지 확인하고, 현재 소스의 영향·안전 조건과 조치 필요성을 구분해 설명합니다. 피해가 작거나 재현되지 않았어도 규칙 위반은 남을 수 있습니다. 반대로 실제 오탐이라도 안전 조건을 명확히 하는 예방 수정은 유용할 수 있습니다. 변경 목적과 승인 범위, 회귀 위험을 확인한 뒤 결정하며, 검출 건수를 줄이기 위한 불필요한 수정은 하지 않습니다.

사례결론 / 작업 상태
수정 필요성을 확인했지만 아직 수정하지 않음fix / analyzed
원래 검출은 오탐이며, 승인된 예방 수정을 완료함false-positive / change-complete
규칙은 적용되지만 정책·허용 조건의 근거가 부족함needs-review / analyzed 또는 deferred

변경 완료는 검증 완료가 아닙니다. 판정 기준과 근거 작성법은 SECURITY_SAST_WORKFLOW.md의 5단계를 참고하세요.

3. 이전 차수와 정책 — 06, 02

이전 차수 자료가 있으면 그 툴킷 또는 백업 경로를 알려주세요.

prompts/06-carry-over.md를 수행해줘. 이전 차수는 ../sast-previous/에 있어.

이전 오탐·예외는 검증 근거와 현재 코드·정책·외부 규격의 유효성을 확인한 뒤 결론을 재사용합니다. 새 차수의 검증 완료는 현재 소스에서 다시 확인합니다. 이전에만 있던 항목은 “이번 차수 미검출”이며, 검사 범위를 확인하지 않고 “해소”로 단정하지 않습니다.

AI는 자료로 확인할 수 없는 업무 사실만 한 번에 하나씩 묻습니다. 선택지에는 동작 차이와 위험이 포함되며 “모르겠다”도 가능합니다. 미확인 기본안에 관찰 로그 등의 변경이 필요하면 그 방법과 영향까지 승인된 범위에서 적용합니다. 답변이나 권한이 없으면 해당 항목을 보류합니다.

결정 정본은 data/decisions.json입니다. project/DECISION_LOG.md는 sync가 만드는 읽기용 기록입니다. 같은 범위의 유효한 정책은 재사용하지만, 기한이나 새 증거가 생기면 다시 확인합니다.

4. 조치와 검증 — 03

초기 분석을 검토하고 scope로 적용된 이번 차수의 처리 범위를 확인하세요.

작업 그룹은 grouping.workGroup으로 묶은 분류 단위입니다. 조치 실행은 이번 요청에서 처리하도록 승인된 범위이며 하나 이상의 작업 그룹을 포함할 수 있습니다.

prompts/03-remediation-wave.md에 따라 적용된 처리 범위 안에서 WG-003을 처리해줘.
승인한 범위에서 그룹 3개를 연속 처리해줘. 정책 질문은 해당 항목을 보류하고 모아서 알려줘.

AI는 수정 직전과 직후에 체크포인트를 저장하고, 검증 직전에 소스 스냅샷을 저장합니다. 검증을 실제 실행한 뒤 그 결과를 소스와 연결합니다. 스냅샷을 만드는 것과 테스트가 통과하는 것은 별개의 일입니다. 소스 수정과 외부 검증의 시작·실제 종료도 각각 기록합니다. 실패한 검증과 다음 재시도는 별도 이력으로 보존합니다. 명령 예와 저장 실패 시 처리는 작업 이력과 실행 로그를 따릅니다.

연속 실행도 승인 범위 안에서만 이어집니다. 추가 권한, 공통 컴포넌트· 외부 규격 영향, 해결되지 않는 오류, 안전한 저장 불가 또는 사용자 중단 요청이 있으면 멈춥니다. 정책 질문이 있는 항목만 보류하고 독립 작업은 계속할 수 있습니다.

혼합 작업 그룹은 query --scope in-scope --group <WG>로 항목별 대상을 나눕니다. 공통 수정이 범위 밖 항목에도 영향을 줬다는 이유만으로 그 항목을 자동 완료하지 않습니다.

중요 변경·공통 코드·오탐·예외는 근거를 직접 검토하세요. 일부 항목만 표본으로 검토했다면 확인한 ID와 선정 기준을 기록하세요. 표본 검토는 나머지 항목의 안전성을 보장하지 않습니다.

5. 대시보드 검토와 백업

SECURITY_CHECKLIST.html은 별도 서버 없이 여는 화면입니다. 브라우저 정책에 따라 로컬 파일이나 저장소 접근이 제한될 수 있습니다.

버튼역할
파일 결과 다시 읽기sync로 생성한 파일 결과를 다시 읽기; sync 자체를 실행하지 않음
답변에서 결과 추출“AI 답변에서 브라우저 초안 만들기” 영역에서 정해진 응답 라벨을 읽어 초안으로 저장
현재 결과 JSON 내보내기현재 항목의 결과를 파일로 내려받기
상태+결과 백업진행상태·비고·상세 결과 초안과 브라우저 변경 이력을 함께 내려받기
상태+결과 불러오기같은 작업공간의 유효한 백업을 항목별로 병합; 더 최신인 현재 값은 유지
읽지 못한 저장본 백업읽기에 실패한 원본이 있을 때만 표시; 그 원문을 보존용으로 내려받기
필터 초기화검색·필터를 초기화

처리 범위 패널에서 값을 고르고 요청을 복사하는 것은 적용이 아닙니다. AI가 scope --min-risk ...를 실행해 정본을 갱신한 뒤 sync·새로고침해야 적용됩니다. 화면 위험도 필터와 필터 초기화, localStorage·백업은 처리 범위를 바꾸지 않습니다.

진행상태별 “분석 완료”, “변경 완료”, “검증 완료” 건수는 서로 누적하지 않고 각각의 현재 상태만 셉니다. “검증 완료 상태 비율”은 전체 검출 항목 중 현재 상태가 verified인 항목의 비율입니다. 검색·위험도·체커·언어 필터로 검토 범위를 줄일 수 있습니다. 작업 그룹은 화면 필터가 아니라 grouping.workGroup 분류와 query --group <WG>로 확인합니다.

“분포 및 추천 작업 보기” 안의 “체커별 진행”은 체커마다 작업 단계를 한 줄 막대로 보여 줍니다. 검증 완료 수/전체 (비율)과 남은 건수를 표시하며, 남은 건수가 많은 체커가 위에 옵니다. 완료는 verified만 세고 보류는 남음에 포함해 따로 표시합니다. 비율은 내림이라 한 건이라도 남으면 100%가 되지 않습니다. 현재 필터 기준으로 집계하고, 체커 이름을 누르면 목록이 그 체커로 좁혀집니다. 기록된 작업 단계일 뿐 현재 소스의 검증 신선도를 증명하지 않습니다. 같은 집계는 query --summary의 byChecker로도 볼 수 있습니다.

“분포 및 추천 작업 보기”를 펼치면 추천 작업의 표시 개수를 선택할 수 있습니다. 추천 목록은 적용된 in-scope 항목에서 검증 완료·보류를 제외한 대상으로, 표의 검색·위험도·체커·언어 표시 필터와는 별개입니다. 처리 범위가 미설정· 잘못된 상태이면 추천 작업을 제공하지 않습니다. 목록이 길면 화면 높이의 절반(최대 480px) 안에서 세로로 스크롤합니다. 제목과 개수 선택기는 목록 밖에 남습니다. Tab으로 목록에 초점을 둔 뒤 키보드로도 스크롤할 수 있습니다. 표시 개수를 바꾸면 목록 맨 위로 이동하며, 표 필터 변경이나 상세 처리 중 목록을 다시 그릴 때는 기존 스크롤 위치를 유지합니다. 항목이 줄어들면 남은 목록의 스크롤 가능 범위로 조정됩니다.

JSON 정본이나 항목별 결과를 바꾼 뒤에는 sync로 JS 미러와 결과 인덱스를 먼저 갱신하세요. 그런 다음 파일 결과 다시 읽기로 생성된 인덱스를 다시 읽습니다. 이 버튼만 눌러서는 JSON 변경이 화면에 반영되지 않습니다.

작업 이력과 시스템 운영 기록

기본 작업 이력에서 어떤 항목을 검토·수정·검증했는지, 상태·판정·메모가 어떻게 달라졌는지 확인합니다. 같은 작업의 시도는 묶어 보여주되 실패와 재시도 결과는 보존합니다. 상태를 화면에서 바꾼 것과 실제 소스 수정은 구분합니다.

동기화·체크포인트 같은 내부 처리는 시스템 운영 기록을 펼쳐 확인합니다. 오류 내용·식별자·원시 전후 값은 해당 기록의 진단 상세에서 봅니다. 저장 실패나 차단처럼 작업에 영향을 줄 수 있는 문제는 기본 화면에도 알립니다. 분류가 불명확한 기존 이력은 분류 미확인으로 남습니다.

항목 상세에서는 현재 차수의 해당 ID 이력을 봅니다. 이전 차수의 같은 ID는 전체 작업 이력에서 차수 표시로 구분합니다. 목록은 페이지당 50개이며, 긴 내용은 높이가 제한된 영역에서 스크롤하고 개별 기록을 펼쳐 확인합니다.

조회·필터는 기록을 삭제하거나 처리 범위를 바꾸지 않습니다. 과거 실패 건수는 현재 미해결 취약점 건수와 다릅니다. 진단 상세는 기존 기록을 보여줄 뿐, 새로운 디버그 수집을 시작하지 않습니다. 분류 기준과 한계는 docs/ACTIVITY_LOG.md를 따릅니다.

종료 기록이 없는 작업은 현재 실행 중이거나 중단됐을 수 있습니다. 화면만으로 원인을 단정하지 않습니다. 마지막 생성·불러온 시각을 확인하고 필요하면 파일 기록을 다시 읽으세요. 화면은 실시간 감시기가 아닙니다.

브라우저에서 저장한 이력은 파일에 가져오기 전까지 브라우저 임시 기록입니다. 상태+결과 백업에 함께 보관하고 04 절차로 출처를 대조합니다. 중요한 이력은 이후 상태 변경으로 지우지 않으며, 파일 가져오기도 정본 결과 반영·검증과는 별개입니다.

브라우저 저장과 파일 저장은 다릅니다

답변을 붙여넣을 때는 조치 결론:에 결론만, 작업 상태:에 작업 단계만 씁니다. 자세한 설명은 판단 이유:에 남깁니다. 예를 들어 예방 수정을 마친 오탐은 조치 결론: false-positive, 작업 상태: change-complete입니다. 작업 상태가 빠진 옛 답변은 분석 완료 초안으로 저장합니다. 결론이 모호하거나 텍스트로 검증 완료를 지정하면 경고를 표시하고 기존 결과를 유지합니다. 변경 완료를 지정했다면 적용 내용:에 실제 변경을 적어야 합니다. 빈 내용은 받지 않지만, 내용이 있다는 사실만으로 실제 변경을 확인한 것은 아닙니다. 파일 결과와 백업은 이 규칙 때문에 자동 재분류되지 않습니다.

  • “브라우저 초안: 저장됨”: 이 브라우저에 상세 결과를 임시 보관했습니다.

  • “브라우저 초안: 현재 화면에만 있음 · 저장 실패”: 아직 저장하지 못했습니다. 화면을 닫기 전에 백업하세요.

  • “정본 대조: 반영 대기”: 아직 파일 결과와 일치하지 않습니다.

  • “정본 대조: 내용 일치”: 읽어 온 파일 결과와 초안 내용이 같습니다. 실제 테스트의 적절성은 별도로 확인해야 합니다.

  • “정본 대조: 정본이 더 최신”: 파일에서 읽은 결과가 브라우저 초안보다 최신입니다. 두 기록을 대조한 뒤 필요한 내용을 반영하세요.

다운로드는 정본 반영의 증거가 아닙니다. 백업을 AI에게 전달해 04 절차로 출처와 근거를 대조하고, 확인한 결과만 파일에 반영한 뒤 sync하세요.

브라우저 데이터는 저장소 삭제·시크릿 모드·용량 제한 등으로 사라질 수 있습니다. 저장 오류가 표시되면 닫기 전에 백업을 내려받으세요. 읽지 못한 저장본은 자동 덮어쓰기를 막습니다. 복구나 불러오기를 시작하기 전에 먼저 [읽지 못한 저장본 백업]으로 원문을 내려받고, 실제 파일이 생성되어 열리는지 사용자가 확인하세요. 화면에 성공 메시지가 보여도 다운로드 성공을 도구가 보장하지는 않습니다. 현재 화면의 새 작업도 [상태+결과 백업]으로 따로 내려받고 실제 파일을 확인합니다. 두 원본을 보존한 다음 04에서 복구를 요청하거나 [상태+결과 불러오기]로 유효한 백업을 직접 불러옵니다. 일반적인 불러오기는 항목별 updatedAt을 비교해 병합하고 더 최신인 현재 값을 유지합니다. 읽지 못한 저장본을 보호 중이었다면 성공한 불러오기가 그 보호 대상 브라우저 저장 항목을 검사·병합한 내용으로 교체합니다. 다른 작업공간이나 식별자가 없는 옛 백업은 원본을 보존하고 04에서 출처를 확인합니다. 검출 ID만 같다고 합치지 않습니다.

6. 중단한 작업 재개 — 07

prompts/07-resume.md로 상태와 이번 차수 처리 범위를 확인하고, 대상인 WG-003 항목부터 이어서 해줘.

재개 시에는 게이트와 원본 상태를 먼저 검사합니다. 손상된 진행상태를 조회하거나 오래된 인덱스로 완료율부터 계산하지 않습니다.

  • 복구는 먼저 미리보기로 확인하고 --apply를 붙일 때만 반영합니다.

  • 결과·체크포인트·누적 이력·백업에 없는 임시 메모는 복구할 수 없습니다.

  • 중간 수정은 현재 diff와 대조해 같은 패치를 중복 적용하지 않습니다.

  • stale: 검증과 연결한 소스 또는 근거가 바뀌었습니다.

  • unbound: 옛 검증에 소스 연결이 없습니다. 현재 소스에서 재검증해야 합니다.

  • fresh: 지정한 파일과 저장된 검증 근거가 일치합니다. 외부 시스템·DB·정책의 유효성까지 보장하지는 않습니다.

  • resumeCandidates: 범위와 관계없는 전체 복구 후보입니다.

  • inScopeResumeCandidates: 현재 처리 범위 안에서 실행할 재개 후보입니다.

  • 작업 로그의 unfinishedAttempts: 종료 기록이 없는 시도입니다. 실제 작업자와 현재 파일을 대조하고 확인한 결과만 기록합니다. 실패로 자동 확정하지 않습니다.

복구는 전체 후보를 보존한 뒤 대상 후보만 상세 실행합니다. 처리 범위가 미설정·손상됐거나 다른 차수의 기록이면 새 상세 작업을 시작하지 않습니다.

자동 재시작·네트워크 재연결·정책 로그 감시는 제공하지 않습니다. 세션을 다시 열어 요청하면 마지막으로 온전히 저장된 기록부터 확인합니다.

7. 결과 대조와 제출 — 04, 05

prompts/04-reconcile-results.md는 브라우저 검토 내용을 정본에 반영합니다. prompts/05-final-evidence.md는 templates/evidence-columns.md에 따라 제출용 xlsx 4종을 만듭니다. 파일명은 프로필의 evidence.outputs에서 정합니다.

제출 전에는 다음을 함께 확인하세요.

  1. validate --strict의 오류와 경고

  2. sast_state.py status의 중간 작업·오래된 검증·연결 없는 검증

  3. 실제 테스트 결과, 미검증·예외·운영 조치의 표시

  4. 제출 파일의 수치·근거·표현과 사용자 검토

  5. 전체·선택 범위·범위 밖(info 포함)·미확인(unknown·누락)의 분리 집계

자동 검사 OK는 데이터 검사 통과입니다. 취약점 해소나 제출 승인을 대신하지 않습니다. 미검증 항목이 있으면 미검증 목록에 명확히 남깁니다. status 출력의 processingScope.selectedComplete는 workflowStatus 기반 단계 집계입니다. 이 값은 status.processingScope.selectedComplete 경로에 있고, selectedReadyForCompletion은 status 출력의 최상위 필드입니다. 완료 보고 전에는 status.selectedReadyForCompletion의 대상 존재·정본 일치· fresh·미완료 체크포인트 없음과 실제 검증 한계를 함께 확인합니다. 선택 범위가 준비돼도 전체 완료나 제출 승인을 뜻하지 않습니다.
