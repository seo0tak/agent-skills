# SAST 조치 워크플로우

## 목적

선택한 SAST 보고서의 검출 결과를 대상 프로젝트의 현재 작업 사본
(이하 "현재 소스")에 대조하여
실제 수정, 오탐, 운영 설정, 예외처리, 추가 검토로 일관되게 분류하고
검증 가능한 결과를 남깁니다.

## 입력 계약

필수 입력은 현재 소스와 이번 차수의 보고서 세트입니다.

- 현재 소스 전체
- 최신 SAST 검출 자료. 다음 중 한 조합:
  (A) 벤더 모드 — 상세 보고서 PDF 1개 이상(분할 허용) + 검출 목록 스프레드시트 1개
  (B) SARIF 모드 — 표준 SARIF 파일 1개(Semgrep, CodeQL, SonarQube 등,
      PDF 선택). 이 경우 아래 본문의 "스프레드시트"는 SARIF results를,
      "PDF 체커 가이드"는 SARIF rules의 설명·help를 가리키는 것으로
      읽습니다.

이전 차수 자료가 없는 경우 재검출 여부를 추정하지 않습니다. 현재 차수와
현재 소스만으로 판단하고 `이전 차수 비교 불가`를 명시합니다.

이전 차수의 툴킷 산출물(findings, progress, security-results)이 있는
경우에는 초기 분석 직후 `prompts/06-carry-over.md`로 오탐·예외 재사용
후보를 찾습니다. 이전 검증과 현재 코드·정책·외부 조건을 대조하고,
새 차수의 verified는 현재 소스에서 재검증합니다. 이월 매칭은 검출 ID가 아니라
`sourceMapping.fingerprint`(파일·함수·검출 코드 지문)를 기준으로 하므로,
소스에 매핑된 모든 검출은 fingerprint를 반드시 기록해야 합니다.

결과 정본은 항목별 `security-results/<ID>.json`입니다.
`data/progress.json`은 결과와 일치해야 하는 집계와 아직 결과가 없는
임시 진행상태·비고를 저장합니다. `data/resume-state.json`은 별도 재개 기록입니다.
`tools/sast_toolkit.py validate`가 이 정합성을 검사합니다.

입력은 `input/` 루트 또는 `input/<세트명>/` 폴더 하나에서 읽습니다.
세트 폴더가 여러 개면 사용할 세트를 지정해야 하며(`--input-set`),
선택된 세트는 게이트 기록에 남아 이후 검증에서 같은 세트로 대조됩니다.
한 차수에는 한 세트만 사용합니다.

## 0단계: 입력 확인

입력 확인은 기계적 검사와 의미 대조로 나눕니다. 먼저
`python3 tools/sast_toolkit.py preflight`를 실행하여 다음을 확인합니다.

- 툴킷 외부에 현재 소스가 존재하는지
- 선택한 모드의 입력 조합이 맞는지(PDF 1개 이상+스프레드시트 1개 또는 SARIF 1개)
- 파일이 비어 있거나 확장자만 바뀐 손상 파일이 아닌지
- 스프레드시트 컨테이너·워크북 또는 SARIF 구조를 읽을 수 있는지

기계적 검사를 통과하면 다음을 보고서 내용과 현재 소스에서 대조합니다.

- 선택 자료가 같은 검사 차수인지(SARIF는 run과 선택 PDF 대조)
- 현재 소스와 선택 자료가 같은 프로젝트인지
- 분석 번호, 생성 시각, 전체 건수가 서로 맞는지
- 벤더 모드의 데이터 시트·헤더 위치와 PDF의 텍스트·이미지 형식
- SARIF 모드의 runs/results/rules를 읽을 수 있는지
- 검출 ID가 중복되지 않는지
- 보고서가 여러 언어 또는 여러 모듈을 포함하는지

결과는 `project/INPUT_VALIDATION.md`와 `data/input-validation.*`에
기록합니다. `python3 tools/sast_toolkit.py gate`가 `GATE: READY`를
반환하기 전에는 프로젝트 초기 분석과 소스 조치를 시작하지 않습니다.
입력 불일치나 확인 근거 부족이 있으면 `BLOCKED`로 기록하고 필요한 자료만
요청합니다.

## 1단계: 프로젝트 초기 분석

보고서를 해석하기 전에 현재 프로젝트를 분석합니다.

1. 모듈과 소스 루트를 찾습니다.
2. 언어, 프레임워크, 런타임 및 빌드 도구를 확인합니다.
3. 테스트 루트와 사용 중인 테스트 프레임워크를 확인합니다.
4. Controller, Service, Repository, Mapper, DTO, Entity, Utility,
   Configuration, Template 및 외부 연동 영역을 식별합니다.
5. 공통 컴포넌트와 업무 도메인 사이의 의존 관계를 확인합니다.
6. 암호화, 인증, 로깅, 직렬화, 파일 처리, 동시성, 외부 프로토콜처럼
   변경 영향이 큰 영역을 표시합니다.
7. 생성 코드, 벤더 코드, 설정 파일, 데이터 마이그레이션 파일처럼 별도
   정책이 필요한 영역을 표시합니다.
8. 실행 가능한 컴파일, 단위 테스트, 통합 테스트 명령을 확인합니다.

결과는 `project/PROJECT_ANALYSIS.md`와 `data/project-profile.*`에 기록합니다.

## 2단계: 보고서 정규화

스프레드시트의 각 항목을 `schemas/findings.schema.json` 형식으로 변환합니다.

필수 정보:

- 순번과 검출 ID
- 위험도와 영향도
- 체커 코드와 체커명
- 언어
- 보고된 파일, 라인, 함수
- 보고서 검출 코드
- 검출 시각 또는 분석 식별 정보
- (있는 경우) 도구 내 처리상태(수용, 예외 승인, 조치확인 등)와 위험도
  원문 표기 — 위험도는 표준 값으로 매핑하고 매핑표를 프로필에 남깁니다

PDF에서는 체커별로 다음을 추출합니다.

- 체커 설명과 보안 목적
- CWE 또는 관련 분류
- 취약 예시
- 해결 예시
- 보고서가 제시한 검출 사유

체커 공통 자료는 `data/checker-guides.*`에 저장합니다. 항목별 확정 가이드로
표현하지 않습니다.

## 3단계: 현재 소스 대조

각 항목에 대해 다음 순서로 확인합니다.

1. 보고된 파일이 현재 소스에 존재하는지 확인합니다.
2. 함수 또는 클래스가 존재하는지 확인합니다.
3. 보고된 라인과 검출 코드가 일치하는지 확인합니다.
4. 라인이 달라졌으면 함수명과 코드 패턴으로 실제 위치를 다시 찾습니다.
5. 타입, null 가능성, 값의 출처, 상태 변경 여부를 확인합니다.
6. 호출부, 반환값 사용처, 저장 위치, 예외 처리 경계를 확인합니다.
7. 같은 원인으로 함께 해소되는 검출을 찾습니다.
8. 같은 파일이지만 원인이 다른 항목은 별도 처리 대상으로 둡니다.

소스 매핑 결과:

- `exact`: 보고서 위치와 현재 소스가 일치
- `relocated`: 동일 코드가 다른 라인 또는 함수 위치에 존재
- `changed`: 주변 코드는 있으나 검출 흐름이 변경됨
- `not-found`: 현재 소스에서 검출 코드를 찾지 못함
- `generated-or-external`: 생성물 또는 외부 소스라 직접 조치 대상이 아님

`not-found`만으로 오탐 처리하지 않습니다. 현재 소스 버전과 보고서 대상
버전이 같은지 먼저 확인합니다.

`exact`, `relocated`, `changed`로 매핑된 항목에는 라인 번호와 무관하게
안정적으로 재식별할 수 있는 `fingerprint`를 기록합니다. 권장 형식은
`<파일 기준 클래스 또는 모듈>.<함수>:<검출 구문 핵심 토큰>`이며, 다음
차수 이월 매칭의 1순위 키로 사용됩니다.

## 4단계: 정책 확인 절차(작업 중 필요할 때마다 적용)

정책 확인은 이 시점에 몰아서 하는 단계가 아니라, 이후 모든 단계에서
코드로 확인할 수 없는 판단이 나올 때마다 적용하는 절차입니다.
6~9단계 진행 중에도 새 정책 질문이 생기면 같은 규칙으로 질문하고
기록합니다.

코드와 보고서만으로 결론을 낼 수 없는 항목은
`SECURITY_GRILL_GUIDE.md`를 따릅니다.

- 질문 전에 관련 소스와 호출부, 그리고 소스 밖 증거(DB 데이터, 폼
  required, profile 설정, 운영 로그)를 조사합니다. 자료로 확인한 사실과
  근거를 먼저 알리고, 사용자가 빠진 조건이나 다른 사실을 정정할 수 있도록 합니다.
- 질문은 한 번에 하나만, 보안 용어가 아니라 업무 사실로 합니다.
- 선택지는 실제 동작 차이, 전제한 업무 조건이 다를 때의 영향과 되돌리기 난이도로 적고,
  "모르겠다"를 항상 둡니다.
- 미확인 기본안은 동작과 잔여 위험을 설명합니다. 사용자가 관찰 방법까지
  선택했고 변경이 승인 범위에 있을 때만 적용합니다. 답변이나 권한이 없으면
  보류합니다. 관찰 기록의 부재를 상황이 없다는 증거로 보지 않습니다.
- 답변은 `project/PROJECT_SECURITY_POLICY.md`와 `data/decisions.json`에
  결정 주체(decidedBy)와 함께 기록하고 sync로 `DECISION_LOG.md`를
  생성합니다. 미확인 기본안에 관찰 방법이 기록되지 않으면 validate 오류입니다.
- 이미 확정된 정책은 동일 범위의 다른 항목에 재사용합니다.

## 5단계: 초기 분류와 작업 그룹

초기 결론 후보:

- `fix`: 실제 취약 흐름이 있고 소스 조치 가능
- `false-positive`: 검출 패턴은 있으나 실제 취약 흐름이 아님
- `operations`: 배포 설정, 비밀값 주입 또는 운영 환경 조치 필요
- `exception`: 외부 규격 또는 승인된 구조 때문에 변경이 부적절
- `needs-review`: 업무 정책이나 외부 명세 확인 전 판단 불가

작업 그룹은 `grouping.workGroup`으로 묶은 분류 단위입니다. 조치 실행은
이번 요청에서 처리하도록 승인된 범위이며 하나 이상의 작업 그룹을 포함할
수 있습니다.

작업 그룹 기준:

- 같은 파일과 같은 근본 원인
- 한 수정으로 함께 해소되는 인접 검출
- 같은 정책 결정에 의존하는 항목
- 함께 검증해야 의미가 있는 호출자와 피호출자

병렬 배정이 가능한 작업 그룹은 수정 파일뿐 아니라 공통 유틸리티, 호출 관계,
테스트 파일, 공유 설정을 기준으로 충돌이 없어야 합니다. 파일 소유권이 겹치면
같은 작업 그룹에 둡니다.

결과는 `project/WORK_GROUPS.md`와 각 finding의 `grouping.workGroup`에 기록합니다.

## 6단계: 항목별 가이드

실제 소스를 수정하기 전에 `security-guides/<ID>.json`을 생성합니다.
동일 원인 그룹은 대표 항목 1개에 전체 가이드를 작성하고 멤버 항목은
`groupGuideRef`와 차이점만 담은 경량 가이드로 대신할 수 있습니다.
대량 동종 검출(수백 건 규모)에서 항목마다 전체 가이드를 반복 생성하지
않습니다.

가이드에는 다음이 포함됩니다.

- 현재 소스 분석
- PDF 공통 가이드의 적용 가능 여부
- 실제 조치 또는 판단 포인트
- 호출부와 영향 범위
- 테스트 계획
- 중복 처리 항목
- 필요한 정책 결정

가이드는 해결책을 미리 확정하는 문서가 아니라 안전한 검토 범위를 지정하는
문서입니다.

## 7단계: 소스 조치

초기 분석과 실제 변경 범위가 승인된 뒤 조치를 시작합니다.
수정 전·후 `tools/sast_state.py checkpoint`로 대상 파일·판단·다음 작업을
저장합니다. 공용 정본은 한 작성자가 담당하고 도구의 협조 잠금을 따릅니다.
중간 작업 재개는 `prompts/07-resume.md`로 현재 소스부터 대조합니다.

1. 현재 프로젝트 관례를 따릅니다.
2. 기존 동작을 보존하는 최소 수정을 우선합니다.
3. 공통 API 또는 함수 시그니처 변경 전 모든 호출부를 확인합니다.
4. 입력 검증은 신뢰 경계에 가깝게 배치하고 중복 검증을 피합니다.
5. 기존 포괄 예외 처리가 안전망이라면 유지하면서 구체 예외를 먼저 처리합니다.
6. 외부 규격, 암호문 형식, 저장 데이터 형식을 임의로 변경하지 않습니다.
7. 설정과 소스 조치를 구분합니다.
8. 이번 조치 실행에 승인된 범위 밖의 정리나 리팩터링을 포함하지 않습니다.

## 8단계: 검증

검증 직전에 `tools/sast_state.py snapshot --id <ID> --path <관련 파일>`로
현재 소스·설정·테스트 파일을 기록합니다. 관련 파일은 --path로 반복 지정합니다.
검증에 사용한 수단을 `verification.method`에 기록합니다. 값은 프로필
`validation.verificationMeans`에 선언된 것 중에서 사용하며, 테스트가
없는 영역은 대체 수단(lint, scanner-recheck, runtime-smoke, manual-review)과 그 한계를
`verification.limitations`에 남깁니다. method 없는 verified는 검증기가
경고합니다.

`SECURITY_TEST_GUIDE.md`에 따라 위험과 영향 범위에 비례해 검증합니다.

- 정적 문법 및 컴파일
- 관련 단위 테스트
- 호출 흐름 회귀 테스트
- 경계값, null, 빈 값, 비정상 입력
- 외부 규격 호환성
- 민감정보 로그 노출
- 동시성 및 공유 상태

검증하지 못한 항목은 사유와 필요한 수동 검증을 기록합니다. 수정이 끝났다는
이유만으로 `verified` 상태를 부여하지 않습니다. 실제 검증 뒤 시각과 결과를
기록하고 `tools/sast_state.py seal-verification --id <ID>`로 스냅샷에 연결합니다.
연결 명령은 검증을 실행하거나 상태를 승격하지 않습니다. stale/unbound 결과는
현재 소스에서 재검증해야 하며 지정하지 않은 외부 조건은 별도로 확인합니다.

## 9단계: 결과 기록

각 항목은 `security-results/<ID>.json`에 기록합니다.

- 조치 결론과 판단 이유
- 실제 변경 파일과 위치
- 적용 내용
- 기존/수정 코드 비교
- 공통 가이드 대비 실제 조치 차이
- 영향 범위
- 검증 명령과 결과
- 중복 처리 항목
- 제출용 비고 문구

`tools/sast_toolkit.py sync`를 실행해 JavaScript 미러와 전체 인덱스를
갱신합니다. `validate`와 `sast_state.py status`로 오류·재개 후보·검증 신선도를
확인합니다. 결과 파일과 체크포인트에 없는 임시 정보를 복원했다고 말하지 않습니다.

## 10단계: 최종 증적

마지막에는 다음 산출물을 생성합니다.

- 전체 조치 결과 스프레드시트
- 오탐 및 예외처리 의견 스프레드시트
- 운영 설정 필요 목록
- 미검증 및 추가 검토 목록
- 위험도별 처리 현황
- 파일별 변경 및 검증 현황

오탐 의견은 번호보다 검출 ID와 파일·함수·검출 코드에 근거합니다. 재검사에서
ID가 바뀔 수 있으므로 파일, 체커, 함수, 코드 지문을 함께 남깁니다.

제출 전 strict 검사, 검증 신선도, 실제 테스트·미검증 목록과 사용자 검토를
함께 확인합니다. 자동 검사 통과는 취약점 해소·제출 승인이 아닙니다.
