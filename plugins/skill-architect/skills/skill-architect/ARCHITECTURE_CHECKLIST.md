# 스킬 아키텍처 체크리스트

## 판정과 근거

각 항목이 실제 목적·입출력·부작용에 필요한지 먼저 판단한다. 아래 예시는
특정 구현을 의무화하지 않는다. 범주 안의 일부 항목만 필요할 수도 있다.

| 판정 | 의미 |
|---|---|
| 적용 | 필요한 범위를 충족한다는 근거가 있음. 근거 수준 이상의 보장을 뜻하지 않음 |
| 부분 | 일부는 충족하지만 필요한 경로나 보장에 확인된 누락·반례가 있음 |
| 미적용 | 필요한 기능/규칙이 없는 것을 관련 파일에서 확인함 |
| 해당없음 | 이 작업의 목적·위험·상태 수명상 필요하지 않음. 이유를 적음 |
| 미확인 | 관련 파일/실행 환경에 접근하지 못했거나 필요한 증거를 아직 확인하지 못함 |

근거 수준은 **지침**(문서의 요구), **구현**(코드 경로·스키마 확인),
**재현**(명령/입력/관찰 결과), **실전**(실제 업무 자료와 환경의 검증)으로
구분한다. 여러 수준이 있으면 함께 적는다. 문서가 있다고 실제 강제를
검증한 것은 아니며, 합성 fixture 성공은 실물 업무 검증이 아니다.
지식형의 출력 안내처럼 문서 자체가 기능인 항목은 지침 근거로 평가할 수 있다.

기계 강제 주장은 관련 구현과 적절한 실패 사례를 확인한다. 실행하지 못한
부분은 구현 확인과 실행 미확인을 함께 적는다. 검증기 파일의 존재나 전체
테스트 통과만으로 모든 규칙이 지켜진다고 판정하지 않는다. 파일에 없는 것과
아직 읽지 않은 것을 구분한다.

범주 요약: 필요한 항목 전부가 충족되면 적용, 확인된 일부 누락이 있으면
부분, 전부 없으면 미적용, 필요한 항목이 없으면 해당없음이다. 판단에 필요한
증거가 남아 있으면 미확인으로 두거나 이미 확인한 부분 판정 옆에 미확인
항목을 명시한다. 발견에는 파일 위치와 발동 조건·영향을, 제안에는 기대
효과·검증 방법을 붙인다. 결함과 선택 개선은 따로 제시한다.

## 1. 트리거 설계

- description이 하는 일과 요청 범위를 설명하는가
- 사용자가 실제 쓰는 언어·표현으로 찾을 수 있는가
- 비슷한 스킬과 혼동할 만한 범용 트리거가 있는가
- 발동 후 첫 행동과 입력이 없을 때의 처리가 명확한가

언어 병기는 대상 사용자가 여러 언어를 쓸 때 평가한다. description 검토와
실제 모델의 발동률 평가는 근거 수준을 나눈다.

## 2. 입력 게이트

- 잘못된 입력을 처리하기 전에 존재·형식·필요한 의미를 확인하는가
- 여러 입력 모드나 범위가 결과를 바꾸면 선택 근거와 모호한 경우의 처리가 있는가
- 승인된 입력의 동일성이 중요한 작업에서 내용 변경 후 재확인을 요구하는가
  (예: 파일 목록과 내용 해시. 경로·크기만으로는 내용 동일성을 보장하지 못함)

단순 파일 변환도 손상·빈 입력 검사가 필요할 수 있다. 2단 승인 게이트나
사람 승인은 입력 오류의 영향과 사용자 요청에 따라 필요성을 판단한다.

## 3. 상태 설계와 기록

- 재사용·재개할 상태의 정본이 하나이며 집계·미러와 구분되는가
- 작업 단위 완료가 기록되고, 유실 시 잘못된 완료로 남지 않는가
- 결과·집계가 양방향으로 맞고 프로젝트/차수 경계를 유지하는가
- 판단 근거와 결정 주체, 필요한 이력이 추적되는가
- 개선 이력을 남기는 모드가 있다면 문제·재현·후보·평가·권한 참조·적용 결과를
  연결하고, 미완료 작업과 완료 결과를 구분하는가

후속 작업이 없는 단회 자문·변환에 별도 상태 저장소를 요구하지 않는다.

## 4. 중단 내성

- 장기 작업을 어떤 파일과 순서로 재개하는지 정해져 있는가
- 반쪽 파일·필수 결과 누락을 감지하고 복구 대상을 지목하는가
- 정본 복구와 집계·미러 재생성 규칙이 구분되는가
- 도구 쓰기가 원자적이며, 재실행 시 중복·덮어쓰기 부작용이 관리되는가
- 재개 시 기록을 검증한 뒤 실제 대상·미완료 수정·평가 최신성을 대조하며,
  후보나 대상 변경으로 무효가 된 평가·권한 참조를 구분하는가

중단 후 처음부터 재실행해도 비용·부작용이 작은 작업은 해당없음일 수 있다.

## 5. 기계 강제 검증

- 중요한 정합성·완료 조건을 실제 검사 경로가 강제하는가
- 스키마와 구현이 필수 필드·타입·enum·참조에서 일치하는가
- 정상 입력을 허용하고 누락·오류·경계 입력을 거부하는가
- 완료/제출 전 필요한 검사가 있고 실패를 성공으로 보고하지 않는가
- 관련 회귀 사례가 있으며 테스트 범위와 실제 업무 검증의 한계가 드러나는가
- 개선 적용 완료를 기록한다면 적용된 내용·버전에 대한 회귀 결과와 복구할
  버전·방법·가용성을 확인한 뒤 검증 완료로 판정하는가

검증기·strict 명령은 수단의 예다. 자연어 자문에 프로그램 검증기를 요구하거나,
감사 스킬이 타 스킬에 권하는 검증 기준을 자기 검증기의 구현으로 세지 않는다.

## 6. 토큰·모델 최적화

- 대량 반복·판단 작업을 나눌 이점이 있고 위임 결과를 확인하는가
- 도구/모델이 없을 때 실행 가능한 폴백과 비용·기능 차이가 명확한가
- 큰 데이터는 필요한 범위로 조회하고 생성 미러·사본을 중복 읽지 않는가
- 반복 내용은 대표+차이 등으로 줄이되 참조가 유효한가
- 모델 선택·탐지·평가 비용이 목적과 품질 요구에 비례하는가

고정 역할과 동적 라우팅 모두 가능하다. 라우팅·벤치마크가 요청된 기능이면
그 자체로 감점하지 않는다. 특정 공급자나 저비용 모델 사용도 보편 의무가 아니다.

## 7. 사람 개입(HITL) 설계

- 판단이 필요한 지점과 실행 권한·중단 조건이 실제 위험에 맞는가
- 이미 승인한 범위에서 불필요한 재승인을 요구하지 않는가
- 독립 작업이 있다면 질문 때문에 전체가 멈추지 않는가
- 사람이 아는 사실로 질문하고, 불확실할 때 처리 방법을 설명하는가
- 기본안의 결과·가역성과 결정 주체·근거를 필요한 수준으로 남기는가
- 비동기 변경을 받는 경우 출처·최신성·충돌·승인 범위를 확인하는가
- 개선 기록의 `approved` 같은 라벨을 실제 사용자 권한과 혼동하지 않고,
  권한 참조가 평가한 후보·대상·평가 결과에 연결되는가

정책 답변을 모를 수 있는 작업에서는 “모르겠다”와 보류/관찰/재검토를 설계한다.
모를 때의 기본 행동은 사용자 목적과 손실 가능성에 따라 정하며, 모든 업무에
동작 보존이나 특정 승인 횟수를 강제하지 않는다.

## 8. 지식 산출물 (필요할 때만)

- 지식을 파일로 재사용·수집하는 요구가 있는가
- 채택한 메타데이터·목록·이력 형식이 정의되어 있고 소비자가 읽을 수 있는가
- 해당 형식의 정본과 생성물, 업무 상태 데이터가 구분되는가

사용자나 저장소의 규약이 우선이다. 별도 규약 없이 지식 파일을 만들기로 했다면
아래 **로컬 지식 규약 v1**을 선택 가능한 최소 형식으로 사용할 수 있다. 외부 OKF 표준의
적합성 인증은 아니며, 외부 규격 준수를 주장하려면 대상 규격·버전·출처를
확인해 별도로 대조한다. 대화 답변이나 형식이 정해진 산출물에는 억지로 붙이지 않는다.

```markdown
---
type: review
title: 입력 검증 감사
description: 합성 입력으로 확인한 검증 범위와 미확인 사항
timestamp: 2026-09-08T09:00:00+09:00
tags: [review]
---
```

이 로컬 규약을 채택하면 `type`은 필수, 나머지는 소비자 필요에 따른 권장이다.
목록이 필요하면 `index.md`에 제목·상대 링크·한 줄 설명을 둔다. 이력이 필요하면
날짜(최신 우선)·변경/결정·이유·근거를 남긴다. JSON 업무 상태는 자신의 스키마를
유지하며 Markdown frontmatter를 추가하지 않는다.

## 9. 문서

- 소비자가 실제 요청 예와 실행·복구 방법을 찾을 수 있는가
- 절차와 원리의 구분이 필요한 규모라면 탐색할 수 있게 나뉘어 있는가
- 실제 실패 상황과 오해하기 쉬운 계약의 예시가 있는가
- 참조 규약·스키마·예제가 독립 설치에서도 접근 가능하고 서로 일치하는가

짧은 스킬에는 한 문서로 충분하다. 특정 파일명이나 별도 치트시트를 의무화하지 않는다.

## 10. 배포

- 실제 배포 대상 하네스가 필요한 파일과 의존성을 발견하는가
- 버전·카탈로그·배포 사본이 일치하고 설치된 버전을 확인할 수 있는가
- 카탈로그 갱신, 설치본 업데이트, 프로젝트 복사본 업그레이드가 구분되는가
- 업그레이드 시 도구와 안내가 함께 갱신되고 사용자 상태·수정본을 보존하는가
- 외부 기능이 없는 환경에서 필요한 폴백 또는 명확한 한계가 있는가

플러그인 배포가 없는 로컬 스킬에는 marketplace/agents 디렉터리를 요구하지 않는다.
