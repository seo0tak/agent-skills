# 작업 방법 모음 (PLAYBOOK)

이 저장소를 만들며 쓴 구조·문서·다이어그램·설계·Claude Code 모드(mod) 기법을 다른 저장소에서도 그대로
쓸 수 있게 정리한 문서다. 이 저장소의 실제 규칙은 `CLAUDE.md`가 정본이고, 여기는 그 규칙이 왜 그렇게
생겼는지와 옮겨 쓰는 법을 적는다.

## 1. 저장소 구조: 정본 하나, 배포 사본은 스크립트로

- 편집 원본은 한 곳(`skills/<이름>/`)이다. 배포용 사본(`plugins/<이름>/skills/`)은 스크립트
  (`scripts/sync-plugins.sh`)가 만들고 손으로 고치지 않는다.
- 심링크 대신 사본을 쓴다. 설치 도구마다 심링크를 다루는 방식이 다르다(한쪽은 실제 파일로 풀고, 다른 쪽은
  빈 디렉터리로 복사했다). 이런 제약은 실제 설치로 확인하고, 그 근거를 문서에 남긴다.
- 같은 값을 여러 곳에 두지 않는다. 버전은 `plugin.json` 하나가 정본이고, 카탈로그에는 쓰지 않는다. 손으로
  맞추는 사본(README 표)은 검사 스크립트(`scripts/check-versions.sh`)가 강제한다.
- 생성물이 있으면 생성 스크립트에 `--check` 모드를 두고 커밋 전에 돌린다. 원본과 생성물이 어긋나면 실패한다.

옮겨 쓸 때: "원본 → 생성물" 관계가 있는 곳마다 생성 스크립트 + `--check` + 커밋 전 실행 목록(`CLAUDE.md`의
"작업 전 확인")을 같이 만든다.

## 2. 문서: 무엇을 어디에 쓰는가

| 문서 | 담는 것 | 담지 않는 것 |
|---|---|---|
| README · SKILL.md · HOW_IT_WORKS · USAGE · 프롬프트 | 지금 어떻게 동작하는지 | 결정 날짜, 대화·질의 번호, 개발 단계 표시 |
| `docs/adr/NNNN-*.md` | 되돌리기 어렵고, 맥락 없이는 의아하고, 실제로 대안을 따진 결정의 이유 | 셋 중 하나라도 아닌 결정 |
| `docs/VERSIONING.md` | 버전마다 바뀐 동작과 업그레이드할 때 알아야 할 것 | 구현 세부 |
| `HANDOFF.md` | 다음 세션이 바로 이어가는 데 필요한 것 | 사용자 안내 |
| `CLAUDE.md` | 에이전트가 지켜야 할 저장소 규칙과 확인 명령 | 이력 |

HANDOFF는 이 순서로 쓴다.

1. 최신 작업 기준: 날짜, 배포 버전, 어느 커밋까지 push했는지.
2. 남은 일: 맨 위에. 화면 확인처럼 사람이 해야 하는 확인도 여기에.
3. 영역별 현재 상태: 지금 모습, 배운 함정, 확인 명령.
4. 이력: 한 줄 화살표(`1.17.0 → … → 1.21.1`)로 줄이고 자세한 것은 VERSIONING으로 보낸다.

"지금 모습"과 "이력"을 섞지 않는 것이 핵심이다. 설계 논의를 마치면 이유는 HOW_IT_WORKS나 ADR에 쓰고,
USAGE·README·SKILL.md에 서로 어긋나는 문장이 없는지 훑는다.

## 3. 다이어그램: 종류별 도구와 검증 가능한 생성물

| 종류 | 도구 | 위치 |
|---|---|---|
| 작업 흐름도 | mermaid | README 안 (GitHub가 바로 그림) |
| HTML 가이드에도 보여야 하는 흐름도 | D2 → SVG | README와 가이드가 같은 SVG를 씀 |
| 구조도 | D2 → SVG | `docs/diagrams/*.d2` |
| 시퀀스 · 상태도 | PlantUML → SVG | `docs/diagrams/*.puml` |

- 원본과 SVG를 함께 커밋한다. 렌더 스크립트(`scripts/render_diagrams.py`)가 SVG 끝에 원본 해시를 넣어,
  `--check`는 도구 없이 해시만 비교한다(CI에서도 돈다).
- D2 SVG에는 너비·높이를 넣는다. 없으면 GitHub에서 작게 나온다.
- 사람이 승인하는 지점이 있는 절차는 시퀀스에 그 지점을 반드시 넣는다. 흐름도·시퀀스·구조도·텍스트 흐름이
  같은 순서와 승인 지점을 보이는지 함께 확인한다.
- 자주 걸린 함정:
  - mermaid가 단어 중간에서 줄을 바꾼다 → 긴 라벨은 `<br/>`로 직접 나눈다.
  - PlantUML 메시지의 `--`가 취소선이 된다 → `~--`로 쓴다.
  - 구조도가 너무 넓다 → 위→아래 배치, 구역을 줄로 쌓는다. 원본 폭이 1,000px를 크게 넘으면 GitHub에서
    글자가 작아진다.
  - 코드 블록 안 명령은 100칸 안으로, 옵션 경계에서 `\`로 나눈다.
- 그린 뒤 눈으로 본다. Playwright로 모든 SVG와 mermaid를 밝은·어두운 배경에서 PNG로 찍어 확인한다. 선이
  상자를 가로지르는 곳, 떨어진 섬, 지나치게 넓은 그림이 이렇게 보인다.

## 4. 설계 진행 방식

- 결정은 사용자가 한다. 질문은 한 번에 한 갈래씩, 권장안을 붙여 묻는다(grill-with-docs 방식). 코드로 답할
  수 있는 것은 묻지 않고 확인한다.
- 큰 단계마다 "착수 전 설계 점검"을 한다. 열린 결정을 좁히고, 위 세 조건을 모두 만족하는 것만 ADR로 남긴다.
- 화면 설계는 시안을 여러 개 그려 한 페이지에서 고르게 한다. 말로 설명하는 것보다 결정이 빠르다. 시안은
  실제로 쓸 수 있는 표현만으로 그린다(예: 터미널 시안은 배경색·글자색·굵게·공백만).
- 설계 리뷰는 점수와 우선순위로 한다. impeccable `critique`로 Nielsen 10개 항목을 0~4로 매기고, 문제를
  P0~P3으로 나눈 뒤 "무엇부터, 어디까지"를 물어 그 범위만 고친다. 리뷰 기록은 `.impeccable/critique/`에 남아
  다음 리뷰에서 점수 추세를 본다.
- 이번에 효과가 컸던 설계 원칙:
  - 한 화면의 숫자는 같은 분모로 맞춘다(범위 기준 요약 옆에 전체 기준 막대를 두지 않는다).
  - 색 하나에 의미 하나. 경보색은 아직 판단이 끝나지 않은 것에만 쓴다.
  - 신호는 절대값이 아니라 상대값으로. 큰 데이터에서 절대 기준은 전부 경보가 된다.
  - 조용한 실패를 없앤다. 빈 화면 대신 원인과 다음 행동을 보여 준다.
  - 설명 문단 대신 범례 한 줄.

## 5. Claude Code 모드(패널) 기법

예시 구현: `plugins/sast-remediation/hooks/register.tsx`, 타입 `types/index.d.ts`, 테스트 `tests/pane.test.tsx`.

### 구조

- 상태는 atom으로 두고, `types/index.d.ts`의 `PluginState`에 키를 선언한다(빠뜨리면 타입 오류).
- 쓰는 훅:
  - `session.start`: 대상 파일이 있으면 패널을 연다.
  - `skill.prompt`: 해당 스킬이 실행되면 연다.
  - `turn.complete`: 주 대화의 턴이 끝날 때 다시 읽는다(서브에이전트 턴은 건너뜀).
  - `session.measure`: 컨텍스트·비용을 받는다. `$.session.usage({ breakdown: 'summary' })`는 로컬 추정이라
    요청을 보내지 않는다.
  - `ui.render`: 그린다. `ui.scroll`: 목록만 스크롤한다.
- 대화가 없는 세션에 띄운 패널은 턴이 끝나지 않아 오래된다. 탭을 누를 때도 다시 읽는다(간격 제한 포함).

### 터미널에서 깨지지 않게

- 화면 종류는 `e.surface`로 가른다. `$.ui.resolve`가 터미널에도 `Svg`를 빈 조각으로 채우므로 `'Svg' in ui`는
  쓰면 안 된다.
- 폭이 모호한 문자(`·` `●` `█` `░` `│`, 상자 테두리, `⚠` `⏸` `★`)는 한글 글꼴 터미널에서 두 칸이 되어
  줄이 잘린다. 쓰지 않는다. `borderStyle`도 쓰지 않는다.
- 아이콘은 항상 두 칸인 이모지(Emoji_Presentation)만 쓰고, FE0F가 붙어야 그림이 되는 이모지는 뺀다.
  아이콘 뒤에 한 칸 띄운다. 테스트가 그려진 트리의 모든 문자를 검사한다.
- 막대는 `backgroundColor`를 칠한 공백으로 그린다. 한글이 섞인 정렬은 `padEnd`가 아니라 칸 수(한글 2칸)로
  계산한다.
- 정렬은 왼쪽 기준. 오른쪽 정렬은 폭 계산이 어긋나면 값이 잘린다.
- 버튼 단축키 색이 강조색과 같으면 글자가 묻힌다. 지금 탭은 버튼 대신 반전 Text로 그린다.

### 반응형과 스크롤

- `e.props.bodyColumns`·`scroll.bodyRows`로 폭과 줄 수를 계산한다. 크기가 바뀌면 엔진이 다시 그린다.
  좁으면 덜 중요한 열을 빼고, 넓으면 이름을 길게 둔다.
- 머리는 고정하고 목록만 움직이려면 `ui.scroll` 훅에서 직접 오프셋 atom을 움직이고 `{}`를 돌려준다.
  해당 없는 경우는 `next(e)`로 엔진이 패널 전체를 스크롤하게 둔다. 위치 안내 한 줄(`2-6 / 10개`)을 둔다.

### 실제 환경에서 배운 것

- Windows: `python3` → `python` → `py -3` 순서로 찾고, Store 바로가기(종료 코드 9009와 안내 문구)는 건너뛴다.
- 프로세스 출력은 4 MiB에서 잘린다. 큰 데이터는 전부 받지 말고, 집계만 출력하는 짧은 스크립트
  (`python -c`)를 돌린다.
- 옛 버전 데이터에 대비한다. 필드가 없으면 직접 세고, 그래도 실패하면 안내 문구를 낸다.
- 테스트가 통과해도 실제 화면(사용자 OS·글꼴·테마)에서 다시 본다. 잘림, 분모 혼동, 겹쳐 보이는 막대는
  스크린샷에서 처음 드러났다.

### 테스트와 검사

- `claude plugin test <플러그인>`: 엔진 쪽 훅(`process.run`, `session.usage`, `fs.*`, `ui.scroll` 등)을 스텁하고,
  `$.ui.mount`로 그린 뒤 `ui.find`·`ui.press`로 문자열과 상호작용을 검사한다. 이벤트는 `$.ui.scroll(...)`처럼
  `$`로 일으킨다.
- 모양을 보고 싶으면 그려진 텍스트를 찍는 임시 테스트를 붙였다가 바로 원복한다.
- `claude plugin validate <플러그인>`, 그리고 플러그인 타입 정의 + hooks + types를 묶은 임시 tsconfig로 `tsc`.

## 6. 작업 습관

- 버전 하나 = 커밋 하나. 코드, 테스트, VERSIONING, README 표, HANDOFF를 같이 바꾸고 검사를 모두 돌린 뒤
  커밋한다.
- push는 요청이 있을 때만. push 전의 실수는 amend로 고치고, push한 뒤에는 새 커밋으로 고친다.
- 보고할 때 "테스트 통과"와 "실제 화면 확인"을 나눠 말한다. 확인하지 못한 것은 확인하지 못했다고 쓴다.
- 실제 마켓플레이스 이름으로 설치 시험을 하지 않는다. 기존 설치·캐시를 지우는 일은 먼저 묻는다.
