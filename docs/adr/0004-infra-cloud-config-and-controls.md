# 인프라 점검은 IaC와 읽기 전용 클라우드 설정까지, 검출은 리소스와 기준 통제 항목으로 묶는다

M4는 저장소의 IaC 파일 점검과 운영 중인 클라우드 계정의 설정 점검(읽기 전용 API)까지 다룬다.
네트워크·호스트 스캔은 실제 트래픽과 침습성 규칙을 새로 설계해야 해서 범위 밖이다. 클라우드
대상은 `aws:<계정>`처럼 제공자와 계정으로 가리키고 점검할 리전 목록을 함께 적는다. 자격증명의
비밀값은 어디에도 저장하지 않고, 스코프에는 쓸 환경의 프로파일·역할 이름과 그것이 읽기
전용이라는 사용자 확인만 남긴다(의미 필드). 스킬은 그 이름을 스캐너에 넘길 뿐 권한이 정말
읽기 전용인지 검증하지 못하며, 이 한계를 숨기지 않는다. 계정·리전 제외는 어댑터가 스캐너 옵션으로
넘겨야 하고 넘기지 못하면 실행·들여오기를 거부한다. 개별 리소스 제외는 읽기만 하므로 결과에서
빼되, 어댑터가 넘길 수 있으면 넘긴다. 인프라 검출의 지문은 리소스 식별자(IaC는 파일+리소스 이름,
클라우드는 ARN 같은 리소스 ID)로, 묶음 키는 CWE 대신 스캐너가 출력한 기준 통제 항목(예: CIS AWS
1.4)으로 만든다. 툴킷은 매핑표를 두지 않고, 매핑이 없는 검출은 스캐너 점검 ID로 묶는다. 스캐너가
통제 항목별 통과·실패·수동을 내면 기준별 건수를 실행 기록에 남기고 표지 보고서에 표로 넣는다.
통과 항목을 검출로 만들지는 않는다. 클라우드 검출은 같은 어댑터가 그 계정·리전·점검 항목을 다시
봤을 때만 해소다. confirmed IaC 결함은 파일을 고치는 코드 조치라 sast-remediation으로 넘기고,
파일이 없는 클라우드 설정 결함은 넘기지 않고 증적에 남긴다.

## Considered Options

- IaC와 기준 대조만 — 가장 작고 안전하지만 운영 중인 설정의 실제 상태를 볼 수 없다.
- 네트워크 스캔까지 — 범위 밖 트래픽·속도·침습도 규칙을 웹처럼 새로 설계해야 해 미뤘다.
- 클라우드는 항상 운영자 실행 — 가장 안전하지만 읽기 전용 점검도 매번 수동이 된다.
- 모든 제외를 스캐너가 지킬 때만 실행 — 대부분의 클라우드 스캐너가 리소스 단위 제외에 약해 자주
  거부된다. 읽기 전용 점검이라 리소스 제외는 결과 필터로 충분하다고 봤다.
- 스캐너 점검 ID로만 묶음 — 단순하지만 스캐너가 다르면 같은 통제 위반이 따로 잡힌다.
- 툴킷이 매핑표를 관리 — 스캐너 간 묶음은 좋아지지만 기준·스캐너가 바뀔 때마다 표를 고쳐야 한다.
- 같은 어댑터 재실행만으로 해소 — 리전 일부만 돌린 실행에서 고쳐지지 않은 결함을 해소로 셀 수 있다.
- IaC 결함을 넘기지 않음 — 인프라 팀이 고치는 경우가 많지만, sast-remediation이 이미 SARIF 파일
  결함을 받으므로 조치 추적을 한곳에 둔다.

## Consequences

- 새 카테고리(클라우드 설정)가 `infra` 대상에 연결된다. 클라우드 스캔은 읽기 전용이라 침습도는
  passive로 선언하지만, 직접 실행에는 여전히 사용자의 명시(ADR 0002)와 스코프의 프로파일·읽기 전용
  확인이 필요하다.
- 스코프 `infra` 대상에 리전 목록과 자격증명 참조(프로파일·역할 이름, 읽기 전용 확인)가 생기고
  인가 지문에 들어간다. 바꾸면 다시 authorize한다.
- 제외 판정이 `aws:<계정>[:<리전>]`과 리소스 ID 접두사를 이해해야 한다.
- 묶음 키가 "지문 + CWE"에서 "지문 + (CWE 또는 통제 항목 또는 점검 ID)"로 넓어진다. 판정 레코드
  키 형식은 그대로 `fingerprint:<키>`다.
- 실행 기록에 기준별 통과·실패·수동 건수와 커버리지(계정·리전·점검 묶음)가 생기고, 표지 보고서에
  기준 대조 표가 들어간다.
