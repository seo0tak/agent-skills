# 방법론 체크리스트는 시험 절차가 아니라 점검 기록 장부다

security-assessment의 방법론 체크리스트는 기준(OWASP WSTG 등)의 항목마다 무엇을 점검했고
결과가 어땠으며 근거가 어디 있는지를 기록하는 장부다. 항목은 ID·제목·표준 문서 링크·필요
침습도·적용 대상 종류만 담은 기준 파일(데이터)에서 오고, 사용자가 이번 점검 범위에 맞는 항목을
고른다. 시험 방법은 표준 문서를 따르며 툴킷에 실행 단계를 적지 않는다 — 스킬은 기성 도구를
조율하는 오케스트레이터이고 공격 절차를 만들지 않는다는 원칙과 같다. 어댑터가 항목 매핑을
선언하고 그 실행의 커버리지가 있으면 "스캔으로 점검됨"을 근거(검출 키·실행)와 함께 제안하되,
항목을 점검함으로 확정하는 것은 사용자다. 항목의 필요 침습도가 스코프 상한을 넘거나 맞는 대상이
없으면 범위 밖으로 두고 점검함으로 표시할 수 없게 한다. 상한을 올리려면 스코프를 바꾸고 다시
인가받는다.

## Considered Options

- 항목마다 수동 확인 절차를 툴킷에 담기 — 스킬의 범위(탐지 오케스트레이션)를 넘고, 절차를 최신으로
  유지하는 부담이 크다.
- 사용자가 항목을 직접 작성 — 가볍지만 기준과의 대조가 약해지고 차수마다 형식이 흔들린다.
- 스캔 결과로 자동 확정 — 빠르지만 스캐너가 항목의 일부만 보는 경우를 구분하지 못한다.
- 스캔과 연결하지 않음 — 단순하지만 이미 스캔으로 덮은 항목을 두 번 적게 된다.
- 범위 판단을 항목마다 사용자에게 맡김 — 범위 밖 확인을 기계가 막지 못한다.

## Consequences

- 기준 파일 형식(항목 ID·제목·링크·필요 침습도·대상 종류)과 항목 상태(범위 밖·미점검·점검함·결함
  발견·해당 없음)가 생긴다. 점검함·해당 없음 확정에는 판정 주체(`decidedBy`)와 근거가 필요하다.
- 어댑터 선언에 선택적 항목 매핑이 생긴다. 매핑은 "이 도구가 이 항목의 일부를 본다"는 제안의 근거일
  뿐 확정이 아니다.
- 표지 보고서에 기준별 진행(범위 안 항목 수, 점검함, 미점검, 결함 발견)이 들어가고, 항목별 근거는
  증적 워크북으로 간다.
- 예시 기준 파일은 일부 항목만 담는다. 전체 목록은 사용자가 표준 문서에서 가져와 같은 형식으로 둔다.
