# 누적 작업 이력 구현·검토 기록

## 범위

사용자 요청에 따라 SAST 작업·실패·차단·중단·재시도와 중요한 변경의 누적 기록,
체크리스트의 전체/항목별 조회를 구현했다. SAST 배포 버전은 1.14.0이며
Architect는 0.4.3을 유지한다. 시작점은 `37f4abf`, 작업 브랜치는
`codex/durable-activity-log`다. 고객 소스·설치본·프로젝트 복사본은 변경하지 않았다.

설계와 실행 계획은 `docs/superpowers/specs/2026-09-15-durable-activity-log-design.md`,
`docs/superpowers/plans/2026-09-15-durable-activity-log.md`에 있다.

## 구현

- 월별 개별 이벤트 JSON에 시작/실제 종료를 분리해 저장하고 자동 삭제하지 않는다.
  같은 이벤트의 같은 내용은 중복 저장하지 않고 ID 충돌은 거절한다.
- 변경 명령은 시작 기록을 먼저 저장한다. 기록 쓰기 실패 시 새 변경을 막고,
  변경 후 종료 기록 실패는 이미 적용됐을 가능성과 대조 필요성을 알린다.
- 체크포인트를 갱신해도 이전 메모·다음 작업이 이력에 남는다. 정본 직접 변경은
  기준 상태와의 차이로 관측하며, 관측을 실제 수정 시각·주체로 포장하지 않는다.
- 브라우저 상태·초안·이력을 함께 저장·백업하며 같은 작업공간의 이전 차수를
  보존한다. 충돌·다른 작업공간 백업은 반영 전에 거절한다.
- 전체 로그는 검색·종류·출처·UTC 날짜 필터와 50건 페이지/내부 스크롤을 제공한다.
  항목별 이력은 현재 차수와 항목을 함께 대조한다. 파일/브라우저 저장 출처를 구분한다.
- 화면 시각은 초 단위 UTC로 읽기 쉽게 표시하되 원본 시각과 내용은 유지한다.
  원문 시각·변경 전후·근거는 펼친 상세에서 확인한다.

## 발견한 문제와 보완

기존 도구의 합성 체크포인트 갱신 시험에서는 최신 메모만 남았고 이전 메모를
자동 복원할 누적 저장소가 없었다. 이 결과를 다른 PC의 실제 손실로 확대하지 않았다.
기존 스킬 요청문을 별도로 읽힌 시험에서도 과거 실패·여러 메모를 수동으로 합치는
방법밖에 없어, 명시적인 시작/종료·재개·대조 명령을 추가했다.

테스트 우선 구현과 독립 리뷰 중 다음 경계를 보완했다.

- 두 탭을 먼저 열고 순차 저장할 때 다른 탭의 이력이 덮이던 문제: 저장 직전 최신 이력 병합.
- 파일 로그와 브라우저 백업의 동일 ID 충돌: 상태 저장 전 전체 대조.
- 여러 항목을 가져오는 작업: 항목별 전후 상태를 별도 기록.
- 큰 관측값 축약: 기록 식별자·해시를 유지해 동일 기준이 계속 새로 생기지 않게 보완.
- 판정 이유·적용 요약·검증 결과·한계와 이전 체크포인트 메모 보존.
- 수정 종료와 검증 종료의 문서상 순서 충돌: 수정 결과 저장 후 수정 시도를 닫고 검증을 별도 실행.
- 재개 요청문에 실제 reconcile 명령과 저장 실패 경계 추가.
- 브라우저 가져오기의 관측 기준 위조와 무관한 작업 ID 재사용을 독립 리뷰에서
  발견해 차단 규칙과 회귀 검사를 보강했다. 최종 재검토 결과는 아래 배포 검증에 기록한다.

## 확인한 실행 근거

- 별도 프로세스의 두 수정 시도, 검증 실패, 종료 없는 재시도, 확인 후 중단 기록,
  새 재시도 성공을 시험했다. 이전 메모·실패가 유지됐고 읽기 전용 status는 파일을
  바꾸지 않았다. 검증 로그 성공 뒤에도 결과의 `change-complete`/검증 `failed`는
  자동 승격되지 않았다.
- 실제 Chromium에 합성 입력과 파일 로그 63건을 열었다. 전체 50/13건 페이지,
  실패 1건·종료 미확인 1건 필터, 항목 이력, 독립 필터 동작을 확인했다.
- 1440px와 모바일 에뮬레이션 390px에서 가로 넘침이 없고 높이 제한 내부 스크롤이
  동작했다. 데스크톱에서 목록에 포커스 후 방향키로 내부 스크롤 이동을 확인했다.
- 두 번의 상태 변경과 두 번의 메모 변경 후 새로고침해 4개 이벤트와 이전/현재
  메모를 확인했다. 백업 버튼의 실제 생성 JSON을 검사하고 파일 입력으로 다시
  가져왔을 때 중복 없이 4개가 유지됐다. 운영체제 다운로드 경로의 파일 보존까지
  확인한 시험은 아니다.
- UI 독립 코드 리뷰와 가독성 후속 재리뷰에서 차단 결함이 없었다.
- 최종 생성 방식의 파일 기록과 UI를 다시 불러와 68건을 조회했다. 예약된 내부
  작업 이름을 넣은 잘못된 백업을 실제 파일 입력에 전달했을 때 오류를 안내했고
  기존 브라우저 저장 내용이 바이트 단위로 유지됐다.

## 배포 검증

- 정본: SAST Python **130**, Node **110**, Architect **24**, 패키징 **1** — 총 **265개 통과**.
- 배포 사본: SAST Python **130**, Node **110** — 총 **240개 통과**.
- JavaScript 구문·변경 공백 검사 통과. `validate`는 배포용 입력 없음 경고 1건만
  반환했다. 실제 작업 로그 디렉터리가 정본과 배포 사본에 포함되지 않은 것을 확인했다.
- Python/JS 공통 입력 검증은 이벤트 26개, 비정상 숫자 3개, 논리 작업 배치 7개
  사례를 대조했다. 예약 action·금지 메타데이터 키·깊이·날짜·작업 정체성을 확인했다.
- 저장부 독립 재리뷰에서 P1/P2 두 건 모두 해결됐으며 수정으로 생긴 새 차단
  결함은 없었다. UI 안전성 재리뷰에서도 새 P1/P2가 없었다.
- main 통합·푸시의 최종 커밋과 원격 반영 상태는 Git 이력으로 확인한다.

## 한계와 운영 주의

강제 종료 순간의 마지막 쓰기, 네트워크 원인 감지, 자동 재시작·외부 백업·법적
불변 보관은 제공하지 않는다. 종료 기록이 없으면 현재 소스·결과·작업자와 대조한다.
파일 저장소 전체에 대한 소스 롤백이나 다중 파일 트랜잭션은 아니다.

미초기화 배포물의 sync/validate는 실제 업무 로그를 만들지 않는다. 명시적으로
기록을 시작하기 전의 오류는 명령 출력으로만 확인한다. 소스 편집·외부 테스트는
명시적인 start/finish와 체크포인트가 필요하다. reconcile은 임의 소스 파일의
모든 편집을 감시하지 않으며 대조 사이에 덮어쓴 중간 상태를 알 수 없다.

브라우저 동시 쓰기 트랜잭션과 입력 중 강제 종료 시 미저장 메모 보존은 보장하지
않는다. 여러 탭의 동시 편집을 피하고 상태+결과 백업을 보관한다. 비밀값 마스킹은
알려진 명시적 패턴에 한정되므로 원시 응답·환경변수·전체 소스를 로그에 넣지 않는다.

호출 가능한 LSP가 없어 제한된 소스 탐색, Python/Node 실행, 실제 브라우저로
확인했다. Windows 실기기·다른 PC·실제 고객 보고서 차수와 설치본 갱신은 미실행이다.
