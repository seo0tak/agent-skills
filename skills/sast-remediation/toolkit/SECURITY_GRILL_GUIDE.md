# Project Security Policy Grill

## 목적

AI가 코드만으로 알 수 없는 프로젝트 정책을 확인하고, 답변을 프로젝트의
재사용 가능한 보안 정책으로 축적합니다. 질문 수를 늘리는 것이 목적이
아니라 같은 판단을 반복해서 묻지 않게 만드는 것이 목적입니다.

이 가이드는 **답하는 사람이 보안이나 이 프로젝트를 잘 모른다**는 전제로
설계되어 있습니다. 레거시를 물려받은 담당자, 처음 SAST 조치를 맡은
개발자가 추천만 누르고 넘어가는 상황을 막는 것이 핵심입니다. 그 원리는
`docs/HOW_IT_WORKS.md`의 "모르는 사람이 써도 안전하다"에 있습니다.

## 질문 시점 원칙

질문이 작업 전체를 세우지 않게 합니다. 웨이브 중 질문이 생긴 항목은
파킹(needs-review + policyQuestions 기록)하고 나머지 작업을 계속한
뒤, 멈추는 시점에 모아 제시합니다. 같은 정책에 걸린 항목들은 하나의
질문으로 병합합니다. 제시는 모아서 하되, 사용자에게는 여전히 한 번에
하나씩 순서대로 묻습니다.

## 질문 전 규칙 — 묻기 전에 찾는다

질문하기 전에 반드시 다음을 수행합니다. 담당자가 몰라도 **시스템은
이미 답을 알고 있는 경우**가 많습니다.

1. 검출 파일과 주변 코드를 읽습니다.
2. 호출부와 반환값 사용처를 확인합니다.
3. 관련 설정과 테스트를 확인합니다.
4. PDF의 체커 설명과 실제 검출 코드를 비교합니다.
5. 기존 `PROJECT_SECURITY_POLICY.md`와 `DECISION_LOG.md`를 검색합니다.
6. **소스 밖의 증거**를 찾습니다. 소스보다 강한 증거가 여기 있습니다.
   - 데이터: DB 스키마의 nullable, 실제 null·빈 값 비율, 저장된 형식
   - 프론트: 폼의 `required`, 입력 마스크, 화면 검증
   - 설정: profile별 값, 환경변수 주입 여부, 기본값 존재
   - 계약: API 문서, 스웨거, 외부 연동 명세, 이전 차수 결정
   - 운영: 로그에 남은 실제 값, 에러 빈도, 재시도 흔적

소스와 증거에서 답이 확인되면 사용자에게 묻지 않습니다. 대신 **확인
결과와 반박 기회**로 제시합니다.

```text
확인 결과: 전화번호는 선택값으로 운영 중입니다.
- users.phone nullable, 실제 null 3,200행 (12%)
- signup.html:41 required 없음
- UserValidator에 phone 검증 없음
이대로 값 없음으로 처리해 12건을 조치합니다. 다르면 말씀해 주세요.
```

틀린 것을 알아채는 일은 정답을 아는 일보다 훨씬 쉽습니다. 담당자는
반박만 하면 됩니다.

7. **두 선택지의 코드 변경이 사실상 같으면 묻지 않습니다.** 답이 무엇이든
   조치가 같다면 기본안을 적용하고 결정 로그에 "선택 무관"으로 기록합니다.

## 질문 방식 — 정책이 아니라 업무 사실을 묻는다

증거로도 갈리지 않는 것만 묻습니다. 물을 때는 다음을 지킵니다.

- 한 메시지에 질문 하나만 합니다.
- **보안 용어로 묻지 않습니다.** "null 정책", "방어적 복사", "fallback
  전략"은 답하는 사람의 언어가 아닙니다. 사용자만 아는 **업무 사실**을
  묻고, 그 사실에서 정책을 도출하는 것은 AI가 합니다.
- 선택지는 원칙이 아니라 **실제 동작 차이**로 적습니다. 파일:줄 근거를
  붙입니다.
- 각 선택지에 **틀렸을 때 무슨 일이 나는지**와 **되돌리기 난이도**를
  적습니다. 초보자도 결과는 비교할 수 있습니다.
- **"모르겠다"를 항상 선택지에 둡니다.** 모르는 사람이 아는 척하게
  만들지 않습니다. 모르겠다를 고르면 기본안을 미확인으로 적용하고
  관찰 장치를 붙입니다(아래 "모를 때의 기본값").
- 이 질문에 **답할 수 있는 사람**이 개발자가 아니면 표시합니다(운영,
  외부 연동 담당, 보안팀). 개발자가 답할 수 없는 질문은 모아서 담당자에게
  넘길 질문지로 뽑을 수 있게 합니다.
- 체커가 낯선 사람을 위해 `checker-guides`의 `plainDescription`(쉽게
  말하면)을 함께 보여줍니다.
- 사용자가 선택하면 즉시 정책과 결정 로그에 기록합니다.
- 같은 범위의 후속 항목에는 확정 정책을 자동 적용합니다.

### 정책 질문을 업무 질문으로 바꾸는 예

| 묻고 싶은 정책 | 실제로 묻는 업무 사실 |
|---|---|
| 이 null은 잘못된 요청인가 값 없음인가 | 이 화면에서 이 항목을 안 넣어도 진행이 되나요? |
| 해시 형식을 바꿔도 되는가 | 이 값을 우리 말고 읽는 시스템이 있나요? 예전 데이터도 같은 형식인가요? |
| 로그 마스킹 정책은 무엇인가 | 장애 때 이 로그에서 실제로 찾아보는 값이 뭔가요? |
| 비밀값 누락 시 기동 실패인가 기능 비활성화인가 | 이 값 없이 서버가 뜨는 환경(로컬·개발)이 있나요? |
| 외부 실패 시 전체 실패인가 부분 성공인가 | 이 연동이 죽었을 때 화면에 뭐가 보여야 하나요? 빈 목록? 오류? |
| 이 객체를 복사해야 하는가 | 이 값을 저장한 뒤에 누가 바꾸나요? |

## 모를 때의 기본값 — 알면 안전한 쪽, 모르면 동작을 보존하는 쪽

`SECURITY_POLICY_BASELINE.md`의 추천 기본값은 **정책이 확인됐을 때**의
기본값입니다. 답하는 사람이 모르겠다고 했거나, 증거가 없어 미확인으로
적용할 때는 다른 기준을 씁니다.

- **확인됨** → 보안적으로 안전한 쪽 (baseline 추천)
- **미확인** → 현재 운영 동작을 보존하는 쪽, 되돌리기 쉬운 쪽

이유: 모르는 사람이 "안전한 기본값"을 대량으로 승인하면 운영이 깨집니다.
모를 때의 기본값은 보안적으로 최선인 쪽이 아니라 **틀려도 사고가 안
나는 쪽**이어야 합니다. 보안 개선은 확인된 뒤에 해도 늦지 않습니다.

미확인으로 적용한 결정에는 **답이 드러나는 장치**를 붙입니다.

- 해당 경로에 관찰 로그(WARN 수준, 비밀값 제외)를 넣어 실제로 그 상황이
  일어나는지 봅니다.
- 결정 로그의 재검토 조건을 "명세 확인 시" 같은 수동 조건이 아니라
  **트리거 가능한 조건**으로 씁니다. "운영 2주 내 이 로그가 찍히면
  선택값 확정, 안 찍히면 필수값으로 재검토."

담당자가 지금 모르는 것은 사실이지만, 2주 뒤엔 알게 됩니다. 조치가
"판단"에서 "관찰"로 바뀝니다.

## 질문이 필요한 대표 조건

각 조건에 확인됐을 때의 추천 기본값과, 업무 사실로 바꾼 질문 예를
둡니다.

### Null과 빈 값

- null이 잘못된 요청인지, 값 없음인지, 기능 비활성화인지
- 빈 문자열과 null이 업무상 같은 의미인지
- 필수 데이터 누락 시 예외, 기본값, 미처리 중 무엇이 맞는지

추천 기본값(확인 시): 필수 입력은 명시적 오류, 선택 입력만 안전한 기본값.
미확인 시: 현재 통과하던 값은 계속 통과시키고 관찰 로그.
업무 질문: "이 화면에서 이 항목 없이 진행이 되나요?"
증거: DB nullable·null 비율, 폼 required, 검증 어노테이션.

### 외부 프로토콜

- 해시, salt, 인코딩, 암호문 형식이 외부 명세에 고정되어 있는지
- 상대 시스템과 이전 데이터가 새 형식을 지원하는지
- 테스트 환경에서 호환성 검증이 가능한지

추천 기본값(확인 시): 명세와 양쪽 사용처가 확인되기 전에는 형식을 변경하지 않음.
미확인 시: 형식 변경 금지 — 이 조건은 확인 전후가 같습니다.
업무 질문: "이 값을 우리 말고 읽는 곳이 있나요? 예전 데이터도 같은 형식인가요?"
증거: 저장된 데이터의 실제 형식, 연동 문서, 상대 시스템 코드.
답할 사람: 대개 외부 연동 담당.

### 로그와 개인정보

- 운영상 반드시 남겨야 하는 필드가 무엇인지
- 마스킹, 부분 마스킹, 제거 중 어느 정책인지
- 보관 기간과 접근 통제가 있는지

추천 기본값(확인 시): 인증정보와 비밀값은 제거 또는 전부 마스킹.
미확인 시: 비밀값·인증정보는 미확인이어도 제거 — 남겨서 얻는 것이 없습니다.
그 외 개인정보는 부분 마스킹.
업무 질문: "장애 때 이 로그에서 실제로 찾아보는 값이 뭔가요?"
증거: 기존 로그 샘플, 로그 조회 도구의 검색 이력.
답할 사람: 대개 운영.

### 설정과 비밀값

- 런타임 주입 방식과 담당 환경
- 값이 없을 때 기동 실패와 기능 비활성화 중 어떤 정책인지
- profile별 기본값을 허용하는지

추천 기본값(확인 시): 필수 비밀값 누락 시 명확히 기동 실패하고 안전하지
않은 기본값을 제공하지 않음.
미확인 시: 기동 실패로 바꾸지 않음 — 배포가 막힐 수 있습니다. 누락 시
WARN 로그를 남기고 어느 환경에서 찍히는지 관찰.
업무 질문: "이 값 없이 서버가 뜨는 환경이 있나요?"
증거: profile별 설정 파일, CI 환경변수, 배포 스크립트.
답할 사람: 대개 운영·배포 담당.

### 예외와 Fallback

- 외부 연동 실패 시 전체 요청 실패, 부분 성공, 빈 응답 중 어떤 정책인지
- 기존 포괄 예외가 장애 격리 목적인지
- 재시도 또는 대체 데이터가 허용되는지

추천 기본값(확인 시): 구체 예외를 먼저 처리하고 기존 최종 안전망은 의미를 보존.
미확인 시: 기존 fallback 동작 보존, 삼켜지던 예외는 삼키되 로그 추가.
업무 질문: "이 연동이 죽었을 때 화면에 뭐가 보여야 하나요?"
증거: 프론트의 빈 응답 처리, 기존 장애 티켓, 재시도 설정.

### 동시성과 공유 상태

- 상태의 소유자가 요청, 세션, 애플리케이션 중 무엇인지
- 초기화 후 값이 변경되는지
- 여러 값을 하나의 불변조건으로 갱신하는지

추천 기본값(확인 시): 요청 상태는 요청 범위에 두고, 초기화 상태는
불변으로 유지하며, 광범위한 직렬화는 피함.
미확인 시: 구조 변경 없이 쓰기 지점에만 최소 동기화.
업무 질문: "이 값이 서버 켠 뒤에 바뀌는 경우가 있나요? 누가 바꾸나요?"
증거: 쓰기 호출부 전수, 관리자 화면·스케줄러 존재.

### Mutable 객체

- 해당 객체가 내부 상태로 저장되는지 임시 계산에만 쓰이는지
- 요소까지 깊은 복사가 필요한지
- ORM 또는 프레임워크가 객체 정체성을 요구하는지

추천 기본값(확인 시): 경계를 넘어 저장·반환되는 mutable 값만 필요한
깊이만큼 복사.
미확인 시: 복사하지 않음 — ORM 정체성이 깨지면 조용히 틀립니다. 반환값
사용처를 관찰.
업무 질문: "이 값을 받아간 뒤에 바꿔서 쓰는 코드가 있나요?"
증거: 반환값 사용처 전수, 엔티티 여부.

## 질문 형식

```text
정책 확인: <업무 사실로 쓴 제목>

쉽게 말하면:
- <체커 plainDescription — 이 검출이 왜 문제인지 한두 줄>

확인한 사실:
- <소스와 증거에서 확인한 내용, 파일:줄>

그래도 모르는 것:
- <증거로 갈리지 않는 업무 사실 한 가지>

선택지:
A) <업무 사실 A> → <실제 동작 차이, 파일:줄>
   틀렸다면: <무슨 일이 나는지>. 되돌리기: <쉬움/어려움>
B) <업무 사실 B> → <실제 동작 차이>
   틀렸다면: <무슨 일이 나는지>. 되돌리기: <쉬움/어려움>
C) 모르겠다 → <미확인 기본안>으로 적용하고 <관찰 장치>를 붙입니다.
   <확인할 방법이나 사람>

추천: <확인됐다면 A/B 중 무엇, 모르면 C에서 어느 쪽 기본안인지>
답할 사람: <개발자 / 운영 / 외부 연동 담당 / 보안팀>
적용 범위: <이 답으로 함께 처리되는 검출 ID 수>
```

## 결정 기록 형식

결정의 정본은 `data/decisions.json`입니다(스키마:
`schemas/decisions.schema.json`, 예시: `examples/decisions.json`).
`project/DECISION_LOG.md`는 `sync`가 거기서 생성하므로 직접 쓰지
않습니다. 항목 하나의 형태:

```json
{
  "id": "DEC-002",
  "decidedAt": "2026-01-01T01:00:00Z",
  "topic": "<업무 사실로 쓴 제목>",
  "question": "<실제로 물은 업무 질문>",
  "recommendation": "<추천안>",
  "decidedBy": "user | baseline-default | choice-irrelevant | deferred",
  "decision": "<확정 결정>",
  "scope": "<자동 적용 범위>",
  "rationale": "<근거>",
  "evidence": ["<확인한 소스·명세·데이터·설정·로그>"],
  "checkers": ["<영향받는 체커>"],
  "findingIds": ["<관련 검출 ID>"],
  "answerableBy": "developer | operations | integration-owner | security-team",
  "exceptions": "",
  "observation": "<baseline-default 필수 — 어디에 무슨 관찰 로그를 넣었는지>",
  "reviewTrigger": "<baseline-default·deferred 필수 — 트리거 가능한 재검토 조건>"
}
```

`decidedBy`가 있어야 고민해서 내린 결정과 추천을 그냥 누른 결정이
기록에서 구분됩니다. 검토자는 `baseline-default`만 골라 볼 수 있어야
합니다. **validate가 강제하는 것**: decidedBy는 네 값 중 하나,
baseline-default에는 observation과 reviewTrigger가 반드시 있어야 하고,
deferred에는 reviewTrigger가 있어야 합니다. 관찰 장치 없는 미확인
결정은 기록될 수 없습니다.

## Grill 종료 조건

- 높은 위험 항목의 판단을 막는 정책 공백이 없음
- 같은 질문을 다시 묻지 않아도 됨
- 외부 규격 및 운영 설정 항목의 담당 경계가 명확함
- 프로젝트 정책과 공통 기준의 차이가 기록됨
- 초기 작업 묶음의 순서와 제외 범위가 확정됨
- 미확인으로 적용한 결정마다 관찰 장치와 트리거 가능한 재검토 조건이 있음
- 개발자가 답할 수 없는 질문이 담당자별 질문지로 정리됨
