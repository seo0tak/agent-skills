# SAST 판정 기록 가이드

## 목적

하나의 결론에 서로 다른 질문을 섞지 않습니다. 각 finding에서 **규칙 적용성**,
**현재 소스의 실제 영향**, **조치 필요성**, **작업 상태**를 독립적으로 확인한 뒤
기존 결과 필드에 근거를 기록합니다. 이 문서는 새 enum이나 스키마 필드를
추가하지 않습니다.

## 네 가지 질문

1. **규칙 적용성** — 보고서가 금지하거나 요구하는 조건이 이 코드에 실제로
   존재하는가? `적용`, `미적용`, `미확인` 중 하나를 판단 근거에 적습니다.
   체커의 정확한 의미가 불분명하면 원본 보고서와 1차 문서를 확인합니다.
   체커 설명·해결 예시가 언어 또는 프레임워크의 공식 계약과 다르면 불일치를
   기록하고 해당 버전의 근거로 대조합니다. 해결 예시를 그대로 적용하지 않습니다.
   소스 주석이나 다른 AI의 설명은 확인할 가설이지 규칙 정의의 증거가 아닙니다.
2. **실제 영향** — 현재 호출자, 입력 타입, 설정과 보완 통제에서 어떤 영향이
   가능한가? 체커가 제시한 최대 이론 영향과 현재 확인된 영향을 구분하고,
   안전 판단에 필요한 전제와 확인하지 못한 경로를 적습니다.
3. **조치 필요성** — `필수`, `예방`, `없음`, `미정` 중 하나를 판단 이유와
   적용 내용에 적습니다. 이 값은 결론 enum이 아니라 기록 문구의 계약입니다.
4. **작업 상태** — 실제로 끝낸 일만 `analyzed`, `change-complete`, `verified`로
   기록합니다. 판정과 작업 진행 정도는 독립적입니다.

## 기존 필드에 기록하는 방법

- `reason`: `규칙 적용성:`, `실제 영향:`, `안전 전제·미확인:`,
  `조치 필요성:`, `결론 근거:` 순서로 간결하게 작성합니다.
- `impact`: 확인된 영향, 최대 영향이 성립하는 조건, 보완 통제와 잔여 위험을
  구분합니다.
- `resultSummary`, `resultFiles`, `resultCodeDiff`: 실제 변경만 기록하고 필수
  조치와 예방 조치를 구분합니다. 변경하지 않았다면 변경했다고 쓰지 않습니다.
- `evidenceNote`: 제출자가 원본 보고서와 현재 소스에서 판정을 재확인할 수 있는
  핵심 근거를 요약합니다.
- `workflowStatus`: 분석만 끝났으면 `analyzed`, 변경까지 적용했으면
  `change-complete`, 현재 소스에 연결된 검증까지 통과했으면 `verified`입니다.

대시보드 응답의 `작업 상태:`에는 `todo`, `in-progress`, `analyzed`,
`change-complete`, `deferred` 또는 화면의 정확한 한국어 값(미착수, 진행 중,
분석 완료, 변경 완료, 보류)을 사용합니다. 새로 파싱하는 응답 텍스트에서 라벨이
없거나 값이 비어 있으면 `analyzed`로 다룹니다. 기존 JSON의 유효한 상태는
그대로 보존합니다. `fix` 결론만으로 `change-complete`를 추론하지 않으며,
`verified`/검증 완료는 응답 텍스트에서 받지 않습니다. 정본 결과의 `verified`는
현재 소스 스냅샷에 연결한 실제 검증 절차로만 부여합니다. 반대로 진짜 오탐에
선택적 예방 변경을 적용했다면 결론은 `false-positive`인 채 작업 상태는 실제
완료 수준을 기록할 수 있습니다.

응답에는 `조치 결론:`을 정확히 하나, 선택적인 `작업 상태:`를 최대 하나만
사용합니다. 중복 라벨이나 작업 상태만 있는 응답은 반영하지 않습니다.
`change-complete`/변경 완료를 명시할 때는 실제 한 일을 `적용 내용:`에 반드시
작성합니다. 비어 있으면 응답을 반영하지 않습니다. 비코드 운영 조치라면
실제 변경 파일이나 코드 차이를 억지로 만들 필요는 없습니다.

## 결론 선택

- `fix`: 규칙이 적용되고 소스 변경이 필요한 경우. 실제 공격 영향이 낮거나
  아직 재현되지 않았어도 유효한 보안·품질·코딩 규칙의 필수 조치일 수 있습니다.
- `false-positive`: 금지된 조건이 타입, 값, 호출 흐름 또는 확인된 프레임워크
  계약 때문에 실제로 성립하지 않는 경우입니다.
- `operations`: 소스가 아니라 배포 설정, 비밀값 주입 또는 운영 조치가 필요한 경우입니다.
- `exception`: 규칙이 적용되지만 확인된 외부 규격 또는 승인된 정책 때문에 즉시
  변경하지 않는 경우입니다. 승인 주체, 범위, 보완 통제와 재검토 조건이 필요합니다.
  적용 가능한 승인 근거가 없으면 `needs-review`입니다.
- `needs-review`: 규칙 의미, 호출 경로, 외부 조건 또는 정책을 확인하기 전에는
  위 결론을 선택할 수 없는 경우입니다.

다음 사유만으로는 오탐이 아닙니다.

- 최대 이론 영향이 현재 확인되지 않았거나 재현하지 못함
- 실제 영향이 낮거나 보완 통제가 있음
- 표준 알고리즘, 의도된 코드, 생성 코드 또는 외부 코드임
- 현재 버전에서 코드가 사라짐
- 수정이 어렵거나 스캐너가 변경을 인식하지 못함

현재 버전에서 코드가 없으면 버전 차이, 이전 수정 또는 위치 변경을 기록합니다.
이는 현재 상태의 근거이지 원래 검출의 오탐 증거가 아닙니다. 표준 알고리즘·외부
규격·생성 코드도 규칙 범위와 실제 계약을 확인한 뒤 `exception`, `fix` 또는
`false-positive`를 선택합니다.

진짜 오탐에도 방어 심화나 가독성을 위한 예방 변경을 선택할 수 있습니다. 그 변경은
오탐 결론을 뒤집지 않으며, 스캐너 통과만을 위한 무의미한 변경을 강제하지 않습니다.

## 그룹과 이관

대표 항목의 결론을 그룹 전체에 복사하기 전에 각 멤버의 입력 타입, 실제 호출자,
설정, 안전 전제와 잔존 동적 경로를 확인합니다. 한 멤버에서 사용자 입력이 원문으로
위험한 사용처에 도달하면 단순 예방 항목이 아니라 실제 조치 검토 대상입니다.

이관할 때는 멤버별 안전 전제, 핵심 호출자·타입·설정과 미확인 사항을 함께 저장합니다.
소스 근거로 확인된 기술 사실과 사용자 또는 운영 조직의 정책 승인을 별도로 기록합니다.
안전 전제가 바뀌거나 제거되면 이전 판정을 그대로 재사용하지 않습니다.

균형 잡힌 합성 사례는 `../examples/determination-cases.md`를 참고합니다.
