# Universal SAST Remediation Toolkit 설계

## 목적

대상 프로젝트의 현재 작업 사본(이하 "현재 소스")에 대해 SAST 검출 결과를
반복 검토·조치하기 위한 워크플로우를 제공합니다. 현재 소스와 이번 차수의
보고서 세트를 입력으로 사용합니다.

- 현재 소스 트리
- 상세 보고서 PDF 1개 이상 + 검출 목록 스프레드시트 1개
  (Sparrow 보고서 기준 안내 포함)
- 또는 표준 SARIF 1개(PDF 선택)

툴킷 자체에는 고객명, 애플리케이션명, 보고서 식별자, 소스 패키지명,
빌드 명령을 포함하지 않습니다.

## 설계 원칙

1. 코드 동작과 라인 위치의 기준은 현재 소스다.
2. 검출 목록의 기준은 선택한 스프레드시트 또는 SARIF results다.
3. 체커 설명은 PDF 또는 SARIF rules에서 출처를 구분해 추출한다.
4. 체커 가이드는 참고 자료이지 항목별 패치가 아니다.
5. 프로젝트 정책 결정은 기록된 뒤에만 다른 검출에 재사용한다.
6. 분석, 조치, 검증은 별도의 워크플로우 단계다.
7. 워크플로우 진행상태와 조치 결론은 별도의 차원이다.
8. 대시보드는 재사용하고 프로젝트 데이터는 별도로 생성한다.
9. 결과 정본은 security-results다. progress는 결과 집계와 결과 없는 임시
   진행상태를 저장하고, resume-state는 재개 지점을 별도로 보관한다.
10. 검출은 ID가 아니라 코드 지문(fingerprint)으로 차수를 넘어
    재식별한다.

## 아키텍처

패키지는 네 계층으로 나뉩니다.

### 1. 고정 툴킷

재사용 가능한 HTML, JavaScript, CSS, 워크플로우, 정책, 프롬프트,
스키마, 검증 도구. 모든 프로젝트에 그대로 복사됩니다.

### 2. 프로젝트 분석

모듈, 소스 루트, 빌드 도구, 테스트 명령, 아키텍처 계층, 외부 연동,
설정 경계, 명시적 결정 없이 변경하면 안 되는 영역을 기술한 생성
파일입니다.

### 3. 보고서 데이터

현재 소스와 선택 보고서로부터 생성한 정규화 프로젝트 프로필,
검출 목록, 체커 가이드. 대시보드는 파일시스템에서 직접 열어도
동작하도록 일반 JavaScript로 이 파일들을 읽습니다.

### 4. 검토 기록

항목별 가이드, 조치 결과, 진행상태, 정책 결정, 증적 워크북. 작업이
진행되면서 생성됩니다.

## 입력 준비 게이트

분석과 조치는 입력 준비 게이트가 `READY`일 때만 시작합니다. 게이트는 두
단계입니다.

1. 기계적 점검(`tools/sast_toolkit.py preflight`): 프로젝트 소스 존재,
   PDF 1개 이상+스프레드시트 1개 또는 SARIF 1개, 실제 형식 검사. 결과는
   `data/input-validation.json`과 `project/INPUT_VALIDATION.md`에
   기록됩니다.
2. 의미 대조(AI): 현재 소스와 선택 보고서가 같은 프로젝트와 같은 검사
   차수인지, 검출 건수와 소스 범위가 맞는지 근거와 함께 판정합니다.

`tools/sast_toolkit.py gate`는 기록된 판정을 현재 입력 파일과 다시
대조하므로, 입력 파일이 바뀌면 이전 승인은 무효가 됩니다. `init`은
게이트가 READY일 때만 진행되고, `validate --strict`도 게이트 통과를
요구합니다.

## 데이터 흐름

1. 입력 준비 게이트를 통과한다 (prompts/00).
2. 검출을 해석하기 전에 프로젝트를 분석한다.
3. 스프레드시트 또는 SARIF results를 표준 finding 스키마로 변환한다.
4. PDF 또는 SARIF rules에서 체커 설명과 가이드를 추출한다.
5. 보고된 파일, 함수, 라인, 검출 코드를 현재 소스와 대조한다.
6. 정확 중복과 동일 근본 원인 검출을 묶는다.
7. 이전 차수 산출물이 있으면 fingerprint 기준으로 오탐·예외 결론을
   이월한다 (prompts/06).
8. 소스와 보고서 근거가 부족할 때만 정책 질문을 한 번에 하나씩 한다.
9. 승인된 답변을 프로젝트 보안 정책과 결정 로그에 저장한다.
10. 소스 변경 전에 항목별 가이드를 생성한다.
11. 초기 분석 검토가 승인된 뒤에만 범위 내 변경을 적용한다.
12. 수정 전·후 체크포인트와 검증 직전 스냅샷을 저장한다.
13. 실제 검증 결과를 소스와 연결하고 결과·진행상태를 갱신한다.
14. sync·validate·status로 정합성·재개 후보·검증 신선도를 확인한다.

## 대시보드 데이터 경계

`SECURITY_CHECKLIST.html`, `assets/checklist.css`, `assets/checklist.js`는
고정입니다. 프로젝트별 데이터는 다음에서 읽습니다.

- `data/input-validation.js`
- `data/project-profile.js`
- `data/findings.js`
- `data/checker-guides.js`
- `data/progress.js`

항목별 상세 기록은 다음에서 읽습니다.

- `security-guides/<finding-id>.js`
- `security-results/<finding-id>.js`
- `security-guides/index.js`
- `security-results/index.js`

JSON이 기계 판독의 기준 기록입니다. JavaScript 미러는 로컬 JSON 요청을
차단하는 브라우저 지원을 위해서만 존재합니다.

## 상태 모델

워크플로우 상태와 결론은 의도적으로 독립입니다.

워크플로우 상태: `todo`, `in-progress`, `analyzed`, `change-complete`,
`verified`, `deferred`

결론: `unreviewed`, `fix`, `false-positive`, `operations`, `exception`,
`needs-review`

이렇게 하면 검증되지 않은 소스 변경을 완료로 취급하지 않으면서,
승인된 오탐이나 예외는 독립적으로 검증완료 표시할 수 있습니다.

결과 정본은 `security-results/<ID>.json`입니다.
`data/progress.json`은 결과와 일치해야 하는 집계 및 결과가 없는 임시 상태입니다.
검증기는 결과가 존재하는 항목의 workflowStatus·conclusion 일치를 검사합니다. enum 정의는 스키마
파일과 검증기 양쪽에 존재하므로 검증기가 교차 검증합니다.

## 진행상태 병합

대시보드는 파일 진행상태(data/progress.js)와 브라우저 localStorage를
병합해 표시합니다. 병합 규칙:

- 항목별 `updatedAt`이 더 최신인 쪽이 이긴다.
- 타임스탬프를 비교할 수 없으면 브라우저 저장본이 이기되, verified는
  강등하지 않는다.
- 값이 다른 항목이 있으면 화면 상단 배너로 방향별 건수를 알린다.
  브라우저에만 있는 변경은 상태+결과 백업으로 내려받아 04에서 대조한다.
- 상세 초안은 draftResults에 별도 보존하며 다운로드를 정본 반영으로 간주하지 않는다.

## 차수 이월

`sourceMapping.fingerprint`는 exact/relocated/changed 매핑에서
필수입니다. 다음 차수에서 검출 ID가 바뀌어도 fingerprint(1순위),
체커+파일+함수(2순위), 체커+파일+검출 코드 패턴(3순위)으로 매칭해
오탐·예외 결론 재사용 후보를 찾습니다. 이전 verified·passed 근거와 현재
코드·정책·외부 규격·기한이 유효해야 결론을 재사용하며 현재 소스에서 재검증합니다.
변경되거나 확인할 수 없는 항목은 needs-review로 둡니다. 상세 규칙은 `prompts/06-carry-over.md`를
따릅니다.

## 정책 확인 절차

에이전트는 질문 전에 코드베이스를 조사합니다. 질문은 한 번에 하나씩,
추천 답변과 함께, 외부 프로토콜 호환성·null 입력의 업무 의미·로그 보관
요건·배포 시 비밀값 주입·동시성 소유권처럼 안전하게 추론할 수 없는
사실로 한정합니다.

승인된 답변은 범위, 근거, 증거, 영향 체커와 함께 기록되고, 새 증거가
결정과 충돌하지 않는 한 이후 검출에 재질문 없이 재사용됩니다.

## 이식성

외부 웹 자산이나 런타임 프레임워크를 사용하지 않습니다. 대시보드는
상대 경로로 로드되고, 지원 도구는 Python 표준 라이브러리만 사용합니다.
도구 자체는 특정 프로젝트 언어나 빌드 시스템을 전제하지 않습니다.
실제 분석·빌드·테스트 가능 여부는 프로젝트와 실행 환경에서 확인합니다.
발견된 명령은 하드코딩 대신 프로젝트 데이터에 저장합니다. 증적 파일명도
`project-profile.evidence.outputs`로 프로젝트별 설정이 가능합니다.

## 중단 복구 경계

sast_state.py는 체크포인트·검증 연결·읽기 전용 현황·복구 미리보기를 제공합니다.
복구 적용은 --apply가 필요하며 원본을 보존합니다. 임시 파일 교체와 협조 잠금은
단일 정본 쓰기 충돌을 줄이지만 다중 파일 트랜잭션이나 분산 저장 내구성을
보장하지 않습니다. 자동 재시작·감시·배포는 비목적입니다.
자세한 데이터 경계와 한계는 HOW_IT_WORKS.md, 실제 절차는 prompts/07을 따릅니다.

## 툴킷 구현 완료 기준

- 고정 툴킷 파일에 프로젝트 식별자가 남아 있지 않다.
- 예시와 빈 데이터가 문서화된 스키마를 준수한다.
- 대시보드가 빈 작업공간과 예시 데이터를 모두 렌더링한다.
- 진행상태 가져오기/내보내기가 상태와 결론을 모두 보존한다.
- HTML 교체 없이 항목별 가이드와 결과를 갱신할 수 있다.
- 검증기가 중복 ID, 잘못된 enum, 필수 필드 누락, JSON/JavaScript 미러
  드리프트, 스키마-검증기 enum 불일치, progress-results 상태 불일치,
  fingerprint 누락을 감지한다.
- 입력 준비 게이트가 READY가 아니면 초기화와 조치가 시작되지 않는다.
- 사전 점검, 초기화, 정책 추출, 이월, 조치, 검증, 증적 생성 지침이
  갖춰져 있다.
