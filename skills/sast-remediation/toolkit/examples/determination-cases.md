# 판정 분리 합성 사례

아래 사례는 기록 방식을 설명하기 위한 가상 코드와 가상 규칙입니다. 특정 SAST
제품의 체커 의미나 실제 프로젝트의 안전성을 주장하지 않습니다. 체커 의미가
불분명하면 원본 보고서와 해당 기술의 1차 문서를 먼저 확인합니다.

## 1. 안전한 바인딩과 원문 치환

가상 SQL 매퍼가 값 입력에 `#{title}`을 사용하고 프레임워크 계약상 준비된 문의
파라미터로 바인딩합니다.

- 규칙 적용성: `미적용` — 가상 규칙이 금지한 원문 SQL 삽입이 아님
- 실제 영향: 문자열 값이 SQL 구조를 바꾸지 않음
- 안전 전제·미확인: 모든 include 결과와 호출 경로가 계속 `#{}` 바인딩을 사용함
- 조치 필요성: `없음`
- 결론/작업 상태: `false-positive` / `analyzed`

반면 정렬 방향 같은 사용자 입력이 `${direction}`으로 런타임 SQL에 직접 들어가고
서버의 허용값 검증을 확인하지 못했다면 실제 조치 검토 대상입니다.

- 규칙 적용성: `적용`
- 실제 영향: 입력이 SQL 구조에 영향을 줄 수 있음
- 안전 전제·미확인: 우회 호출과 서버 측 allowlist가 미확인
- 조치 필요성: `필수` 또는 근거 확인 전 `미정`
- 결론/작업 상태: 근거에 따라 `fix` 또는 `needs-review` / `analyzed`

MyBatis의 `#{}` 파라미터 처리, `${}` 원문 치환과 include property 동작은
[공식 SQL 매핑 문서](https://mybatis.org/mybatis-3/sqlmap-xml.html)를 기준으로
확인합니다.

## 2. 같은 안전 조건이 제거된 차수

이전 차수에는 타입이 제한된 enum 경계만이 유일한 안전 전제였고 서버 측
allowlist는 없었습니다. 현재 호출자 하나가 그 타입 경계를 우회해 임의 문자열을
원문 사용처에 넘기도록 바뀌었습니다.

- 규칙 적용성: `적용`으로 재검토
- 실제 영향: 새 호출 경로에서 구조 제어 가능성이 생김
- 조치 필요성: `필수`
- 결론/작업 상태: `fix` / `analyzed`

이전 `verified`를 복사하지 않고 새 호출자와 현재 소스에서 다시 검증합니다.

## 3. 영향이 낮아도 적용되는 품질 규칙

가상 코딩 규칙이 자원 정리를 요구하며 현재 경로의 데이터 노출이나 서비스 중단은
재현되지 않았지만 누락된 정리 경로가 실제로 존재합니다.

- 규칙 적용성: `적용`
- 실제 영향: 현재 확인된 영향은 낮음, 장시간 반복 시 자원 고갈 가능성은 남음
- 조치 필요성: `필수`
- 결론/작업 상태: `fix` / 변경 전 `analyzed`

최대 보안 영향을 재현하지 못했다는 이유로 `false-positive`로 바꾸지 않습니다.

## 4. 예외 승인 대기와 승인 완료

외부 프로토콜이 특정 레거시 형식을 요구해 규칙은 적용되지만 즉시 변경하면
상호운용성이 깨집니다.

- 승인 대기: 조치 필요성 `미정`, 결론 `needs-review`, 작업 상태 `deferred`
- 승인 완료: 승인 주체·범위·보완 통제·기한·재검토 조건을 기록하고 결론
  `exception`, 작업 상태 `analyzed`

기술 계약을 확인한 사실과 조직의 위험 수용 승인을 별도 근거로 남깁니다.

## 5. 진짜 오탐과 선택적 예방 보강

가상 규칙은 신뢰할 수 없는 문자열의 원문 SQL 삽입을 금지합니다. 검출된 `${id}`의
실제 타입은 서버가 생성한 정수이고 모든 호출자가 같은 타입 경계를 거치므로 현재
규칙의 금지 조건은 성립하지 않습니다. 향후 호출자 타입 변경에 덜 의존하도록
승인된 예방 변경으로 `#{id}` 바인딩을 적용했습니다.

- 규칙 적용성: `미적용`
- 실제 영향: 현재 정수 값은 임의 SQL 구문을 전달할 수 없음
- 조치 필요성: 보안 수정은 `없음`, 적용한 보강은 `예방`
- 결론/작업 상태: `false-positive` / `change-complete`

실제 검증과 스냅샷 연결을 마치기 전에는 응답 텍스트로 `verified`를 쓰지 않습니다.

## 6. 근거가 부족한 항목

검출 구문은 찾았지만 실제 입력 타입, 동적 호출자와 운영 설정을 확인할 수 없습니다.

- 규칙 적용성: `미확인`
- 실제 영향: 최대 영향 조건과 현재 영향 모두 확정 불가
- 안전 전제·미확인: 타입, 호출자, 설정
- 조치 필요성: `미정`
- 결론/작업 상태: `needs-review` / `analyzed`

주석이나 이전 요약을 안전성 증거로 승격하지 않고 필요한 확인 자료와 재개 조건을
기록합니다.

## 7. 이메일 모양 리터럴과 실제 개인정보 영향

가상 규칙이 소스의 이메일 모양 리터럴 자체를 금지하고 코드에
`demo.user@example.invalid`가 있다면 “더미”라는 설명은 패턴 적용을 취소하지
않습니다. 규칙 적용성은 `적용`이며 조치 필요성은 규칙과 서버 계약에 따라
판단합니다. 실제 개인정보인지, 외부로 전송·저장·로그되는지, 클라이언트가 요구하는
sentinel 값인지는 실제 영향과 안전 전제의 별도 근거입니다.

반대로 원본 규칙이 실제 개인식별정보만을 대상으로 한다면 예약된 합성 값이 그
조건에 해당하는지 따로 확인합니다. “저장하지 않음”이라는 주석만으로 데이터 흐름을
증명하거나, 서버 계약을 확인하지 않고 필수 검증 우회 값을 제거하지 않습니다.

## 8. 내부 시프트 값으로 제한된 알고리즘

가상 규칙이 “외부 입력 시프트 값을 범위 검사 없이 사용”하는 경우만 금지하고,
모든 시프트 거리가 내부 상수 또는 확인된 범위 제어에서 나온다면 규칙 적용성은
`미적용`이 될 수 있습니다. “표준 알고리즘”이라는 이름만으로 오탐 처리하지 않고
호출자와 값 출처를 확인합니다. 언어의 시프트 거리 동작은
[Java 언어 명세 15.19](https://docs.oracle.com/javase/specs/jls/se8/html/jls-15.html#jls-15.19)처럼
대상 버전의 1차 문서로 확인합니다.
