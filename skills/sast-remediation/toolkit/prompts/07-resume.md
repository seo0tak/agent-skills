# 중단한 작업 재개 요청문

새 세션에서 진행 중인 차수를 이어갈 때 사용합니다. 이 스킬은 스스로
세션을 다시 열거나 네트워크 복구를 기다리는 실행기가 아닙니다.
사용자나 실행 환경이 다시 시작한 뒤, 파일에 남은 기록으로 재개합니다.

```text
진행 중인 SAST 조치 작업을 안전하게 이어서 진행해 주세요.

1. 입력과 실행 범위를 확인합니다.
   툴킷 디렉터리에서 python3 tools/sast_toolkit.py gate를 실행합니다.
   READY가 아니면 조치를 재개하지 않습니다. 입력 변경·옛 승인 해시 누락은
   prompts/00과 docs/VERSIONING.md에 따라 의미 대조부터 다시 확인합니다.
   현재 요청 또는 확인 가능한 승인 근거의 범위만 사용합니다.
   과거 파일 기록만으로 연속 실행·배포·추가 소스 변경 권한을 추정하지 않습니다.
   동일한 승인 범위가 확인되면 세션이 바뀌었다는 이유만으로 다시 묻지 않습니다.

2. 집계를 사용하기 전에 정본 상태를 검사합니다.
   python3 tools/sast_state.py status
   python3 tools/sast_toolkit.py validate
   두 명령의 오류, resumeCandidates, pendingCheckpoints와
   verification의 fresh/stale/unbound 상태를 읽습니다.
   손상된 progress를 먼저 query하거나 오래된 index로 완료를 판단하지 않습니다.

3. 필요한 항목만 복구합니다.
   - progress 손상·누락:
     python3 tools/sast_state.py recover-progress
     먼저 미리보기를 읽습니다. 같은 작업공간의 백업이 있으면 --backup <파일>로
     다시 미리봅니다. 충돌·출처·복구 불가 정보를 확인한 뒤 같은 명령에
     --apply를 붙여 반영합니다. 도구가 보존한 원본과 입력 백업을 유지합니다.
     결과 레코드, 체크포인트, 백업에 없는 임시 상태·메모는 복구할 수 없습니다.
     draftResults는 보존 대상이지 자동으로 정본 결과가 되는 자료가 아닙니다.
   - 개별 result·guide 손상: 원본을 보존하고 해당 ID만 근거와 소스로 재검토합니다.
     기록 없이 판단 이유나 검증 성공을 재구성하지 않습니다.
   - JS 미러·index 불일치: JSON 정본을 확인한 뒤 sync로 다시 생성합니다.
   - 잠금 충돌: 실행 중인 작성자가 있는지 확인합니다. 다른 프로세스가
     작업 중인데 잠금 파일을 삭제하거나 저장을 강행하지 않습니다.
   복구 범위가 불명확하거나 자료가 없으면 해당 항목을 보류하고 필요한 입력을 요청합니다.

4. 중간 수정과 오래된 검증을 대조합니다.
   세션, 프로젝트 루트, 대상 언어, 브랜치·리비전, worktree·현재 파일 내용이
   바뀌었거나 언어 서버가 다시 연결됐으면 이전 탐색 기능·인덱스 상태를 무효로
   보고 다시 확인합니다.
   SECURITY_SAST_WORKFLOW.md의 「소스 탐색 계약」에 따라 현재 파일이 반영됐는지
   알려진 심볼로 교차 확인합니다. 실패·오래되거나 불완전한 인덱스·참조 0건은
   영향 없음의 증거가 아니며, 신뢰할 수 없으면 텍스트 탐색과 실제 소스,
   컴파일/린트/테스트로 대체하고 불확실성을 알립니다.
   before-edit/after-edit 체크포인트의 대상 파일·메모·다음 작업을 현재
   diff와 대조합니다. 소스가 이미 바뀌었다면 같은 패치를 다시 적용하지 않습니다.
   stale은 연결된 소스 또는 근거가 바뀐 상태, unbound는 옛 검증에 소스 연결이
   없는 상태입니다. 두 경우 모두 현재 소스 검증을 다시 하기 전에는 완료로 신뢰하지
   않습니다. 과거의 passed나 verifiedAt만 복사해 새 연결을 만들지 않습니다.
   fresh는 지정한 파일과 기록이 연결 시점의 내용과 일치한다는 뜻입니다.
   외부 정책이나 운영 환경의 타당성까지 확인한 결과는 아닙니다.

5. 원본이 정리된 뒤 sync, validate, query --summary 순서로 현황을 봅니다.
   project/WORK_GROUPS.md와 새 security-results/index.json을 대조하고,
   query --group <WG>로 재개 후보를 확인합니다. todo뿐 아니라 in-progress,
   deferred, needs-review와 소스 재검증 후보를 포함합니다.

6. data/decisions.json과 project/PROJECT_SECURITY_POLICY.md를 읽습니다.
   유효한 동일 범위 정책은 재사용합니다. 새로운 증거·기한·reviewTrigger가
   있으면 재검토하며, 도구가 자동으로 로그를 감시했다고 말하지 않습니다.
   미해결 질문은 해당 항목에 연결해 하나씩 묻고, 승인 범위의 독립 작업은 계속할 수 있습니다.

7. 이전 판정의 조건을 다시 확인합니다. 그룹 멤버별 안전 전제, 핵심 호출자·입력
   타입·설정과 잔존 동적 경로를 현재 소스에서 대조합니다. 안전 조건이 제거됐거나
   미확인 경로가 생기면 이전 오탐·예외를 그대로 재사용하지 않습니다. 소스 근거로
   확인한 기술 사실과 정책 승인·위험 수용을 분리하고, 규칙 적용성·실제 영향·조치
   필요성과 workflowStatus를 각각 갱신합니다.

보고할 내용
- 복구한 기록, 보존한 원본, 복구하지 못한 정보
- 상태별 건수와 검증 신선도, 중간 수정이 발견된 항목
- 남은 그룹·정책 질문·다음 작업
- 계속 사용할 승인 범위 또는 추가로 필요한 사용자 결정

범위가 확인되면 prompts/03의 체크포인트 → 수정 → 스냅샷 → 실제 검증 →
결과 기록·연결 → sync/validate 순서로 이어갑니다.
```
